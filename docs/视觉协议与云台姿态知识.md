## 0. 先看这 6 行（导读）

1. 视觉串口 = **USART1 / 115200 / 8N1**，帧头是**两个 ASCII 字符 `'A' 'A'`（0x41 0x41）**，不是单字节 0xAA；MCU 发 43 字节、收 29 字节。
2. 包内角度的**单位是弧度**（`VISION_ANGLE_UNIT_RAD = 1`），而云台内部**全部按度**标定 —— 换算是唯一容易全线错 57.3 倍的地方。
3. 我们发给视觉的 `pitch` 填的是 `user_attitude.qe_roll`，因为那个 EKF 里的 `Roll` 名字叫 Roll、数学上却是**绕 Y 轴的俯仰**（轴交换，见 1.3.3 与 2.3.7）。
4. 云台有**两套完全不同的角度坐标系**：`gimbal->pitch` 是**关节角**（编码器零点，水平 = +9.1403°），`gimbal->yaw_fb` 是**世界角**（IMU）。混用它们就是这个项目 2026-10-25 那个"越近越上抬"bug 的根因（见 2.6.4）。
5. 6 轴 IMU 的 **yaw 一定会漂**（重力对 yaw 完全无感），pitch/roll 不漂（有重力做绝对参考）—— 这决定了 `bias_accum` 这套机制为什么存在。
6. 前馈（feedforward）不是"玄学增益"，是**运动学换算**：1 RPM = 6 deg/s。理论系数 1.0/0.1667 是精确值，实际取 0.45 是被**视觉角速度噪声**逼的（见 2.7.4）。

## 1.1 物理层

| 项目 | 值 | 出处 |
|---|---|---|

| 波特率 | **115200** | L49 |
| 数据/停止/校验 | **8 / 1 / None（8N1）** | L50–L52，`UART_MODE_TX_RX`、`HAL_UART_OVERSAMPLING_16` |
| 引脚 | **PB7 = RX，PA9 = TX**（AF7） | L138–L153 |

| **帧长** | MCU→视觉 **43 B**，视觉→MCU **29 B** | `VISION_TX_PACKET_SIZE` / `VISION_RX_PACKET_SIZE` |
| 字节序 | 小端（STM32 原生） | 结构体直接上线上发 |

**带宽账（自己算一遍，别信感觉）**

```
115200 8N1 → 每字节 10 bit（1 起始 + 8 数据 + 1 停止）
           → 115200 / 10 = 11520 B/s 上限
发 43 B @ 100 Hz = 4300 B/s = 37.3%  ← 与 user_vision.h L58-61 注释的 "约 37%" 一致
收 29 B @ 100 Hz = 2900 B/s = 25.2%
双向合计          = 7200 B/s = 62.5%（还剩 37.5% 余量）
单帧线上时间：43 × 10 / 115200 = 3.73 ms（周期 10 ms，空闲 6.27 ms）
若改成 1 kHz：43 kB/s，是上限的 3.7 倍 → 队列灌满、UART 长期忙 → 所以否决
```

**为什么发包跑在主循环而不是 1 ms 定时器里**：`user_vision.c` L39–52 的 `Vision_LoopHandle` 用 `HAL_GetTick()` 自计时，挂在 `loop_event[]` 上。主循环慢一点只会让发送率轻微下降，不会占 1 ms 中断预算。

**取帧方式（重要，决定你能看到什么现象）**：`RingBuffer_GetWith_H_Len()` 在环形缓冲里**从最后一个可能的帧起点往前找**帧头，找到就拷 `len` 字节并把读指针推过去 —— 也就是说：

> 一次回调里缓冲若堆了 3 帧，**只解析最新那一帧，前面 2 帧被直接丢掉**（丢旧保新，不是排队）。

所以 100 Hz 发送 + 主循环偶尔变慢，表现是"`frame_count` 涨得比 100/s 慢"，而不是"数据延迟堆积"。`VISION_RX_MAX_PER_LOOP = 4` 这个循环上限因此很少真正跑满 4 次。

## 1.2 两个结构体（内存布局 = 线上布局）

```c
/* 视觉 -> 电控：29 字节 ------------------------------------------------ */
typedef struct __attribute__((packed)) {
    uint8_t  head[2];      /* 0  'A','A'                      */
    uint8_t  mode;         /* 2  VISION_RX_MODE_xxx           */
    float    yaw;          /* 3  目标 yaw（包内单位：rad）      */
    float    yaw_vel;      /* 7  目标 yaw 角速度（rad/s）       */
    float    yaw_acc;      /* 11 目标 yaw 角加速度（rad/s^2）   */
    float    pitch;        /* 15 目标 pitch（rad）             */
    float    pitch_vel;    /* 19 目标 pitch 角速度（rad/s）     */
    float    pitch_acc;    /* 23 目标 pitch 角加速度（rad/s^2） */
    uint16_t crc16;        /* 27 覆盖前 27 字节，小端           */
} VISION_RX_PACKET;

/* 电控 -> 视觉：43 字节 ------------------------------------------------ */
typedef struct __attribute__((packed)) {
    uint8_t  head[2];        /* 0  'A','A'                    */
    uint8_t  mode;           /* 2  VISION_TX_MODE_xxx         */
    float    q[4];           /* 3  w,x,y,z（无量纲）           */
    float    yaw;            /* 19 当前世界 yaw（rad）         */
    float    yaw_vel;        /* 23 世界 yaw 角速度（rad/s）     */
    float    pitch;          /* 27 IMU 俯仰（rad）             */
    float    pitch_vel;      /* 31 pitch 电机角速度（rad/s）    */
    float    bullet_speed;   /* 35 弹速（m/s）                 */
    uint16_t bullet_count;   /* 39 剩余弹量（发）               */
    uint16_t crc16;          /* 41 覆盖前 41 字节，小端         */
} VISION_TX_PACKET;
```

> **`packed` 不是可选项**：不加它，编译器会在 `uint8_t mode` 后面插 1 字节把 `float` 对齐到 4 字节，包长会从 43 变成 44/48，视觉侧再也对不上。加了 `packed` 之后 GCC 生成的是**不做对齐假设**的访问序列（逐字节 / 非对齐 LDR），Cortex-M4 能跑；但**你绝不能用 `(float*)&buf[3]` 这种强制转换去读**——`VLDR` 要求 4 字节对齐，非对齐会直接 UsageFault（见 1.6 坑 1）。

### 1.3.1 `mode` 的三档（代码里其实只有两档在用）

`user_vision.h` L80–83 定义了 4 个值，`gimbal.c` 只发其中 2 个：

| 值 | 宏 | 现在的填写条件 | 状态 |
|---:|---|---|---|
| 0 | `VISION_TX_MODE_IDLE` | `gimbal->yaw_auto <= 0.5`（操作手没开自瞄） | ✅ 在用 |
| 1 | `VISION_TX_MODE_AUTOAIM` | `gimbal->yaw_auto > 0.5` | ✅ 在用 |
| 2 | `VISION_TX_MODE_SMALL_BUFF` | 小符（打符模式） | ⚠️ **全工程无写入点，未实现** |
| 3 | `VISION_TX_MODE_BIG_BUFF` | 大符 | ⚠️ **同上，未实现** |

**关键设计（别改成看 `aim_takeover`）**：这里用的是**使能开关 `yaw_auto`**，不是"本拍是否真的在接管"。

- 因为 `mode` 是和视觉的**握手**：只有先告诉视觉"AUTOAIM"，它才会开始发 `mode=1/2` 的控制包；
- 如果改成看 `aim_takeover`（而它又依赖 `mode != 0`），就形成 **"等对方先动"的死锁** —— 双方都永远不开始。代码注释 L432–434 专门写了这一条。

### 1.3.2 `q[4]` —— 四元数，且**已经和 yaw 字段同基准**

四个数是 **w, x, y, z**（Hamilton 约定，实部在前）。来源 `user_attitude.qe_q[0..3]`（EKF 输出），但**发出去之前绕世界 Z 轴补了一个 −bias_accum 的旋转**（L442–454）：

```c
b_half = 0.5f * Wrap180(gimbal->bias_accum) * DEG2RAD;
qc = cosf(b_half);  qs = sinf(b_half);          /* q_rot = (qc, 0, 0, -qs)  */
tx_qw = qc*qw0 + qs*qz0;                        /* q_out = q_rot ⊗ q_in     */
tx_qx = qc*qx0 + qs*qy0;
tx_qy = qc*qy0 - qs*qx0;
tx_qz = qc*qz0 - qs*qw0;
```

**为什么要补这一下**：`yaw` 字段发的是 `imu_yaw − bias_accum`（扣过零偏），而 `q` 是 EKF 原始输出（含未修正的 yaw 漂移）。如果两个字段基准不同，视觉用 `q` 建坐标系、用 `yaw` 做目标角，就会**一边漂一边算**，闭环反而更差。补完之后 `q` 的 yaw 和 `yaw` 字段一致（差一个 0.6° 的示例见 1.5.1）。

上面 4 个式子是**标准 Hamilton 积** `q_rot ⊗ q_in` 展开，可以逐项验算：

- `w = w1w2 − x1x2 − y1y2 − z1z2`，代入 `(qc,0,0,−qs)` 得 `qc·qw0 + qs·qz0` ✅
- `z = w1z2 + x1y2 − y1x2 + z1w2`，得 `qc·qz0 − qs·qw0` ✅

> ⚠️ 代码**没有**在发送前再做一次归一化。模长靠 EKF 内部保证（`user_quaternion_ekf.c` L240–244 有 `invSqrt` 归一化），误差在 1e-5 量级，可以接受；但如果你以后把 `qe_q` 换成别的来源，**必须自己归一化**（原因见 2.3.4）。

### 1.3.3 `pitch` 为什么填 `qe_roll`（轴交换）

代码 L422–427：

```c
#if VISION_PITCH_USE_IMU_ONLY          /* 当前 = 1 */
    const float tx_pitch = user_attitude.qe_roll;      /* ← 不是 qe_pitch！ */
#else
    const float tx_pitch = user_attitude.qe_pitch + gimbal->pitch;
#endif
```

证据链（三段，缺一不可）：

1. `user_quaternion_ekf.c` L205–207 用四元数反解欧拉角，写的是**标准 ZYX**（yaw-pitch-roll）公式，但**变量名标错了**：

   | 代码里的名字 | 实际公式 | 数学上它是什么 |
   |---|---|---|
   | `QEKF_INS.Yaw` | `atan2(2(q0q3+q1q2), 2(q0²+q1²)−1)` | 正确的 yaw ψ ✅ |
   | `QEKF_INS.Pitch` | `atan2(2(q0q1+q2q3), 2(q0²+q3²)−1)` | **roll φ**（标准 roll 公式） |
   | `QEKF_INS.Roll` | `asin(−2(q1q3−q0q2))` | **pitch θ**（标准 pitch 公式 `asin(2(q0q2−q1q3))`） |

   验证：`2(q0²+q1²)−1 = 1−2(q2²+q3²)`、`2(q0²+q3²)−1 = 1−2(q1²+q2²)`（因为 `|q|=1`），所以三个式子对得上标准 ZYX 解。

2. 参考工程 `dvc_bmi088.cpp:524-527` 明确写了"`QEKF_INS.Roll` 实际是绕 Y 轴的俯仰角"，`Data_Euler.pitch = QEKF_INS.Roll`。
3. `gimbal.c` L423–426 的实测结论：包里 `pitch` ≈ 四元数解出的 roll，两个独立样本都验证过。

**给视觉的语义**：这个 `pitch` 是 **IMU 的世界俯仰角（0° = 水平，正 = 抬头）**，**不是**云台的关节角。记住这一点，2.6.4 的 bug 就是从这儿来的。

`VISION_PITCH_USE_IMU_ONLY` 这个开关的含义（`user_vision.h` L63–70）：

| 值 | 发什么 | 适用条件 |
|---:|---|---|
| 0 | `qe_pitch + gimbal->pitch` = IMU 俯仰 + 编码器俯仰 = **枪口世界仰角** | IMU 装在 **yaw 框架**上（看不到枪管自己转） |
| 1 | 只发 IMU 俯仰 | IMU 装在 **pitch 框架**上（跟着枪管一起转）—— **参考工程填法** |

判定法（注释给的）：**只转枪管**，看串口绘图 `qpitch` 变不变 → 变 = IMU 在 pitch 框架上（填 1），不变 = 在 yaw 框架上（填 0）。

> ⚠️ **`#else`（填 0）那一支本身也有轴交换问题**：它写的是 `user_attitude.qe_pitch + gimbal->pitch`，而 `qe_pitch` 按 2.3.8 的分析**实际是 roll**。也就是说"填 0"这条路径同时混了 roll 和关节角。**当前 `= 1` 没有启用它，所以问题没暴露**；但如果你按上面的判定法决定改成 0，必须先把 `qe_pitch` 换成 `qe_roll`，否则会叠加两个错误。

> ⚠️ **这里注释和配置是矛盾的**：`gimbal.c` L420–421 写"本车 IMU 在 yaw 框架上 → 枪口世界仰角 = IMU俯仰 + 编码器俯仰"，`gimbal.h` L244–249 也写"IMU 装在 yaw 与 pitch 的连接处"（`GIMBAL_IMU_ON_GIMBAL = 1`），**但宏取的是 1（只发 IMU）**。按注释的逻辑本车应该填 0。到底填哪个取决于 `qpitch` 实测，属于**待确认项**（附录 B #1）——而这正是 2.6.4 那个 bug 的土壤。

### 1.3.4 `yaw` / `yaw_vel` —— 单位弧度，而且一个扣了零偏一个没扣

```c
/* 发出（L460–461），VISION_DEG2PKG = 0.0174532925f */
yaw      = Wrap180(imu_yaw - bias_accum) * VISION_DEG2PKG;   /* deg → rad，扣零偏 */
yaw_vel  = user_attitude.yaw_rate       * VISION_DEG2PKG;    /* deg/s → rad/s，未扣 */
```

- `imu_yaw` = `Wrap180(Attitude_Get_Yaw(&user_attitude))`（`gimbal.c` L319），来自**陀螺积分的 yaw**，不是 EKF 的 yaw。
- `bias_accum` 是零偏累积角（deg），所以 `yaw` 字段就是**位置环用的同一个 `yaw_fb`**（`gimbal.c` L514 `world_yaw`）。这一点很重要：视觉的世界系和云台闭环的世界系是**同一个基准**，漂移速度也一致。
- `yaw_vel` 没扣 `yaw_bias`，带着约 0.05 deg/s（`gimbal.h` L113 的实测值）的偏差 —— 当作前馈用时，0.05 deg/s × 0.45 = 0.02 deg/s 的指令，**可以忽略**，但要知道它不是"干净"的。

### 1.3.5 `pitch_vel`

```c
gimbal->pitch_speed * 6.0f * VISION_DEG2PKG      /* L463 */
```

`pitch_speed` 是 GM6020 反馈的转子转速 **RPM**；**1 RPM = 360/60 = 6 deg/s**（这个换算后面出现十几次，背下来）。所以这一项是"枪管关节角的角速度"，单位 rad/s。

### 1.3.6 `bullet_speed` —— m/s，由摩擦轮 RPM 换算

```c
/* L467–470 */
bullet_speed = user_shooter.friction_rpm_filt      /* RPM，FIR 滤波后 */
             * VISION_RPM_TO_RAD_S                 /* 0.10471976 = 2π/60 */
             * VISION_BULLET_SPEED_COEF;           /* 0.03 */
```

**公式**：

```
v [m/s] = RPM × (2π/60) × 0.03 = RPM × 0.0031416
```

| 摩擦轮 RPM | 角速度 rad/s | 发出弹速 m/s |
|---:|---:|---:|
| 3000 | 314.16 | 9.42 |
| 6000 | 628.32 | **18.85** |
| 7500 | 785.40 | 23.56 |
| 8000 | 837.76 | 25.13 |

**0.03 这个系数的物理含义**：`v = ω·r`，系数 0.03 m/s per rad/s ⇔ **等效摩擦轮半径 30 mm（直径 60 mm）**。如果换成直径 42 mm 的轮子，理论系数应变成 0.021（`待实测标定`，注释也强调"换个摩擦轮/电压就得重标"）。

> ⚠️ **坑**：摩擦轮没开时 `friction_rpm_filt = 0` → 发出 `bullet_speed = 0.0`。视觉若拿它解弹道，`v0 = 0` 会直接除零 / 解出无意义角度。建议视觉侧对 `v < 5 m/s` 做保护，或电控侧在发送时把下限钳到标定值（**这是建议，当前代码没有钳位**）。

### 1.3.7 `bullet_count` —— 现状：硬编码 0

```c
Vision_Set_Tx_Bullet(&user_vision, /*speed*/, 0U);   /* L470 */
```

真实弹量要接**裁判系统**（RoboMaster 官方串口协议），本车没接，所以恒发 0。**语义上视觉应当把 0 理解成"不知道"，而不是"没弹了"** —— 这一条必须和视觉组对齐，否则它可能因为 `count==0` 拒开发射请求。

### 1.3.8 `crc16` —— CRC-16/MODBUS

```c
/* user_vision.c L18–37 */
uint16_t Vision_CRC16(const uint8_t* data, uint16_t len) {
    uint16_t crc = 0xFFFFU;                 /* init 0xFFFF */
    for (i...) {
        crc ^= data[i];
        for (j = 0; j < 8; j++) {
            if (crc & 1) crc = (crc >> 1) ^ 0xA001U;   /* 反射 poly 0xA001 */
            else         crc >>= 1;
        }
    }
    return crc;                             /* 无最终异或 */
}
```

| 参数 | 值 |
|---|---|
| 名称 | **CRC-16/MODBUS**（多项式/反射方式与 CRC-16/ARC 相同，**但初值是 0xFFFF 而不是 0x0000**，别拷错表） |
| 初值 | `0xFFFF` |
| 多项式 | `0x8005` 反射 → **`0xA001`** |
| 输入/输出反射 | 是（右移算法） |
| 最终异或 | 无 |
| **覆盖范围** | **整包除最后 2 字节**：发送 0..40（41 B），接收 0..26（27 B） |
| 存储顺序 | 小端（低字节在前） |

**手算校验值（本文示例包，可直接拿去对拍）**：

- 发送包 41 字节 → `crc = 0xC59A` → 线上字节 `9A C5`
- 接收包 27 字节 → `crc = 0xEF7F` → 线上字节 `7F EF`

任何语言实现只要参数一致，结果必须**一模一样**；差一个 bit 就是"永远离线"（每包都判坏帧）。Python 快速验证：

```python
def crc16(data: bytes) -> int:
    crc = 0xFFFF
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc
assert crc16(bytes.fromhex("41 41 01 B2 9D 77 3F 00 00 00 00 00 00 00 00 96 E7 81 3E "
                           "3A 5C 03 3F C7 B8 B2 3D 39 FA 0E BD 94 D9 20 3E "
                           "FB CB 96 41 00 00")) == 0xC59A
```

### 1.4.2 离线判定 `VISION_OFFLINE_MS = 50`

```c
/* user_vision.c L177–183，在 Vision_Update 里（100 Hz 调用） */
if (is_online != 0 && (HAL_GetTick() - last_rx_ms) > VISION_OFFLINE_MS) {
    is_online = 0;  timeout_count++;
}
```

| 项目 | 值 | 说明 |
|---|---|---|
| 阈值 | **50 ms** | 100 Hz 下一帧 10 ms → 相当于**连续丢 5 帧**判掉线 |
| 检测粒度 | 10 ms | 判定只在 `Vision_Update`（100 Hz）里跑 → **实际发现延迟 50~60 ms** |
| 掉线后数据 | **保持不清零** | 只置标志；"保持还是回手动"由应用层决定 |

**为什么视觉离线阈值（50 ms）和云台自瞄超时（`GIMBAL_AIM_TIMEOUT_MS = 120 ms`）不一样**：两级串联，语义不同。

```
视觉停发
  → 50~60 ms：is_online = 0        → 云台每拍 Release（回摇杆），但保留"最近有效帧时刻"
  → 120 ms  ：aim_ms 超时          → Gimbal_Aim_Abort()：退出接管 + 锁存"必须来一帧合格数据才重接管"
```

中间的 50~110 ms 是**"短丢帧"窗口**：云台已经听摇杆了，但还没认定"视觉真的没了"，所以视觉一恢复就立刻重新接管，不用操作手干预（`gimbal.c` L1149–1160）。

### 1.5.3 时序（30 ms 窗口）

```text
时间(ms)   0     3.7            10    13.7          20    23.7        30
MCU 发送   ├─43B─┼──────────────┼─43B─┼─────────────┼─43B─┼───────────┤
线上占用   ██████ 3.73ms          ██████               ██████
视觉回包       ├─29B(2.52ms)─┤         ├─29B─┤            ├─29B─┤
DMA空闲中断     ↑ 每包收完触发一次 → 环形缓冲 → 主循环 Vision_Handle
主循环           ↑ 取最新一帧 → CRC → 更新 target_* / frame_count / last_rx_ms
云台 1kHz                          ↑ Gimbal_Aim_Update 发现 frame_count 变了才校验（L1183）
```

关键点：
- **收发独立**：发送在 `loop_event`（主循环），接收在 DMA 中断 + 主循环回调，两边不互等。
- **云台 1 kHz vs 视觉 100 Hz**：`Gimbal_Aim_Update` 只在 `frame_count` 变化时才跑闸门（L1183），否则**一帧会被误判成"连续 10 帧无效"**→ 5 帧就退出接管（`GIMBAL_AIM_INVALID_LIMIT = 5`）。这是必须记住的设计。
- 一帧 29 B 在 115200 下占 2.52 ms，所以视觉 100 Hz 是完全发得出来的。

## 1.6 常见坑（按踩到的概率排序）

**坑 1：字节对齐 / 结构体 packed / 非对齐访问**

- 不加 `__attribute__((packed))` → 编译器插填充字节 → 包长变 44/48 → 视觉永远对不上帧。
- 加了 `packed` 之后，**`float` 落在偏移 3、7、19…（非 4 字节对齐）**。Cortex-M4 的普通 `LDR` 支持非对齐，但 **FPU 的 `VLDR` 要求字对齐**，非对齐直接 UsageFault。GCC 对 packed 成员不会生成 `VLDR`，所以现在能跑；但**你绝对不能写 `float* p = (float*)&buf[3];`**。要读就 `memcpy(&f, buf+3, 4)`。
- 反过来，**在 PC 上（x86/ARM64）这段代码也可能"看起来正常"**，所以别用 PC 端小脚本"验证"对齐问题，它会骗你。

**坑 2：小端**

STM32、x86 都是小端，视觉侧若是 x86/ARM 也没问题。但如果视觉跑在**大端**平台（少见），或者你用"手工拼字节"的方式组包，就必须自己按小端拼：`crc16` 是 `低字节在前`（0xC59A → `9A C5`）。**用结构体直发就天然正确**，这也是本工程的做法。

**坑 3：CRC 覆盖范围**

- 发送：`Vision_CRC16(&tx_packet, 43-2)` = 前 **41** 字节，**不含** crc16 自己。
- 接收：`Vision_CRC16(&rx_packet, 29-2)` = 前 **27** 字节。
- 常见错误：把 crc 字段也算进去（永远不等）、或者只算数据段不算帧头（第一版最容易犯）。

**坑 4：单位混用（本项目最容易翻车的一条）**

| 层次 | 单位 | 证据 |
|---|---|---|
| 包内 | **弧度 / 弧度每秒 / 弧度每秒²** | `VISION_ANGLE_UNIT_RAD = 1` |
| `user_vision.target_*` | **弧度**（原值透传，不换算） | `user_vision.c` L140–146 |
| `user_vision.target_*_deg` | 度（**只给绘图用**） | L159–164 |
| `gimbal->` 全部控制量 | **度 / 度每秒** | `gimbal.h` L16–24 明确写"内部全部按度标定" |
| BMI088 `gyro[]` | **rad/s** | `gimbal.h` L20–23 |
| `yaw_bias` / `bias_accum` | **deg/s、deg** | 同上 |

`gimbal.h` L44–53 的开关就是为这个准备的：**"若上电后发现云台转角差 57.3 倍，把这个开关翻一下"**。翻开关必须**两边同时改**（视觉 + 电控），只改一边就是灾难。

**坑 5：帧头不是 0xAA**

`VISION_FRAME_HEAD` 是字符串 `"AA"`，取帧时按 `strlen("AA") = 2` 匹配两个字节 `0x41 0x41`。串口助手 HEX 模式下要**按 `41 41` 找**，搜 `AA` 是搜不到的。命名沿用参考工程，别以为是 bug。

**坑 6：一次回调只解析最新一帧（丢旧保新）**

见 1.1 末尾。所以"`frame_count` 涨得慢"不等于"丢包"，可能是主循环变慢导致旧帧被丢。要看真实链路质量应该看 `crc_error_count`（坏帧）而不是 `frame_count`。

**坑 7：CRC 错了就整包丢，不要"猜"**

`user_vision.c` L134–137：CRC 不对 → `crc_error_count++` 然后 `continue`，**绝不把半包数据写进 target**。因为坏帧的 float 可能是任意值（包括 NaN），直接拿去控制会把云台甩飞。这条原则在后面"六道闸"里又强化了一次。

**坑 8：`bullet_speed = 0` 时视觉可能除零**

见 1.3.6。摩擦轮没开 / 还没起转时，`friction_rpm_filt` 是 0。

**坑 9：`mode` 的握手死锁**

见 1.3.1。改 `Vision_Set_Tx_Mode` 的判断条件前先想清楚会不会双方互等。

## 2.1 表示三维姿态的三种方式

| | **欧拉角**（yaw/pitch/roll） | **旋转矩阵** R（3×3） | **四元数** q（4 个数） |
|---|---|---|---|
| 参数个数 | 3 | 9（含 6 个约束） | 4（含 1 个约束 \|q\|=1） |
| 直观性 | ★★★ 人直接能懂 | ★ 全靠算 | ★★ 需要训练，但有几何意义 |
| **万向节死锁** | **有**（见 2.2） | 无 | 无 |
| 插值/求平均 | 差（跨 ±180° 会绕圈） | 差（要正交化） | **好**（slerp / 归一化平均） |
| 复合旋转 | 要按顺序乘 3 个矩阵 | 矩阵乘法（9×3 次乘加） | **四元数乘法（16 次乘加）** |
| 数值漂移 | 无（但会跳变） | 累积误差会失去正交性 | 只需重新归一化 |
| 反解角度 | 直接就是 | 有公式 | 有公式（2.3.7） |
| 本工程用在哪 | 人机接口：遥控、串口绘图、软限位、PID 误差 | 不直接出现（隐含在四元数里） | **发给视觉的 `q[4]`**、EKF 内部状态 |

**一句话结论**：**内部算用四元数，和人交互用欧拉角，中间用公式来回转**。本工程正是这个结构：EKF 内部是四元数，`gimbal->pitch/target_yaw` 全是欧拉角（度）。

## 2.2 欧拉角与万向节死锁 ★

### 2.2.1 先明确"顺序"

欧拉角三元组 **离开顺序就没有意义**。同一个 `(30°, 20°, 10°)`：

- **ZYX 顺序**（先绕 Z 转 yaw，再绕新的 Y 转 pitch，最后绕新的 X 转 roll）→ 航空/云台惯用
- **XYZ 顺序** → 机械臂惯用

矩阵写法（ZYX，也就是本工程 `user_quaternion_ekf.c` 用的那套）：

```
R = Rz(yaw) · Ry(pitch) · Rx(roll)
```

`R` 是从**机体系**到**世界系**的旋转（把机体坐标下的向量变到世界坐标）。

### 2.2.2 死锁是怎么发生的（数学）

取 `pitch = 90°`，代入：

```
Ry(90°) = [ 0  0  1 ]
          [ 0  1  0 ]
          [−1  0  0 ]

Rx(roll) = [ 1    0       0    ]
           [ 0  cos r  −sin r  ]
           [ 0  sin r   cos r  ]

Ry(90)·Rx(r) = [ 0   sin r   cos r ]
               [ 0   cos r  −sin r ]
               [−1    0       0   ]

再左乘 Rz(y):
R = [ 0    sin(r−y)   cos(r−y) ]
    [ 0    cos(r−y)  −sin(r−y) ]
    [−1      0          0      ]
```

**矩阵里只剩下 `(r − y)` 这一个量** → yaw 和 roll 变成**同一根轴**，两个自由度塌成一个，**丢了一个自由度**。

### 2.2.3 ★ 具体数字例子

| 三元组 | 矩阵 R（只列第 1、2 列） | 结果 |
|---|---|---|
| `yaw=30°, pitch=90°, roll=0°` | `[0, sin(−30), …; 0, cos(−30), …; −1, 0, …]` = `[0,−0.500,…; 0,0.866,…; −1,0,…]` | r−y = −30° |
| `yaw=0°, pitch=90°, roll=−30°` | `[0, sin(−30), …; 0, cos(−30), …; −1, 0, …]` = `[0,−0.500,…; 0,0.866,…; −1,0,…]` | r−y = −30° |

**两组差 30° 的欧拉角，描述的是同一个姿态**，只有 `φ−ψ = −30°` 有意义。

这在云台上会表现成什么？

> 云台 pitch 已经顶到 90°，你继续打杆让 yaw 从 30° 转到 0°。数学上它必须同时把 roll 从 0° 变到 −30° 才能保持同一个朝向 —— 而**真实的云台没有 roll 轴**，它做不到。于是：
> - 解算器算出"yaw 变了 30°，roll 也要变 30°"；
> - 你只能丢掉 roll，姿态就**跳变**了 30°；
> - 表现为**锁定点附近失控 / 突然甩头 / 目标丢失**。

### 2.2.4 ★ 为什么大疆云台只在 ±30° pitch 内工作

死锁点附近，yaw 的计算对输入噪声的**放大倍数是 1/cos(pitch)**：

| pitch | 1/cos(pitch) | 视觉 yaw 噪声 0.1° 被放大成 | 结论 |
|---:|---:|---:|---|
| 0° | 1.00 | 0.10° | 正常 |
| **28.6°（本车上限）** | **1.139** | 0.114° | 完全可接受 |
| 45° | 1.414 | 0.141° | 还行 |
| 60° | 2.000 | 0.200° | 开始难受 |
| 80° | 5.759 | 0.576° | 抖 |
| 85° | 11.47 | 1.147° | 不可用 |
| 90° | ∞ | ∞ | 死锁 |

本车的软限位 **−10.8° ~ +28.6°**（`GIMBAL_PITCH_MIN_DEG` / `MAX_DEG`）→ **最大 1.139 倍**，离死锁非常远。这不是巧合，是机械设计刻意避开的：**机械行程限制本身就是防死锁的第一道防线**。

> ⚠️ 顺带一个结论：如果你哪天用 `target_pitch` 直接写一个 45° 以上的值（比如弹道解算没钳位），**先别怀疑 PID** —— 先去查 `Gimbal_Clamp_Pitch_Target()` 有没有被绕过（`gimbal.c` L249–256）。

## 2.3 四元数（重点，讲透）

### 2.3.1 定义与几何意义

单位四元数 `q = w + xi + yj + zk`，四个实数，满足 `w² + x² + y² + z² = 1`。

**几何意义（唯一需要记住的一条）**：

> 绕**单位轴** `n = (nx, ny, nz)` 转 **θ** 角，则
>
> ```
> w = cos(θ/2),   (x, y, z) = n · sin(θ/2)
> ```
>
> 即 `q = (cos(θ/2),  nx·sin(θ/2),  ny·sin(θ/2),  nz·sin(θ/2))`

**记住"半角"**：角度在 cos/sin 里**除以 2**。四个数的平方和自动等于 1（因为 `cos²+sin²=1`），这就是约束的来源。

### 2.3.2 ★ 例子 1：绕 Z 轴转 30°、60°

| 转角 θ | θ/2 | w = cos(θ/2) | z = sin(θ/2) | 四元数 (w,x,y,z) |
|---:|---:|---:|---:|---|
| 30° | 15° | 0.96593 | 0.25882 | **(0.966, 0, 0, 0.259)** |
| 60° | 30° | 0.86603 | 0.50000 | **(0.866, 0, 0, 0.500)** |
| 90° | 45° | 0.70711 | 0.70711 | (0.707, 0, 0, 0.707) |
| 180° | 90° | **0** | **1** | (0, 0, 0, 1) |

**这个表要看出两件事**：

1. **转 180° 时 w = 0**（这就是"q 和 −q 表示同一姿态"的由来：转 180° 的正反方向恰好重合）。
2. **不是线性的**：θ 从 30° 到 60°（翻倍），z 从 0.259 到 0.500（**不是** 0.518）。所以**四元数不能当"角度"直接相加**。要复合旋转必须用乘法（2.3.3）。

### 2.3.3 ★ 例子 2：同一姿态的欧拉角与四元数，为什么会差一个"顺序"

设一个姿态：**先绕世界 Z 转 90°（yaw），再绕新的 Y 转 45°（pitch），roll=0**。

**欧拉角写法**：`(yaw, pitch, roll) = (90°, 45°, 0°)`，ZYX 顺序。
**四元数写法**：必须按同样顺序乘：

```
q = qz(90°) ⊗ qy(45°) ⊗ qx(0°)
  = (0.70711, 0, 0, 0.70711) ⊗ (0.92388, 0, 0.38268, 0)
  w = 0.70711×0.92388 − 0 − 0 − 0.70711×0            = 0.65328
  x = 0 + 0 + 0 − 0.70711×0.38268                    = −0.27060
  y = 0.70711×0.38268 − 0 + 0 + 0                    = +0.27060
  z = 0 + 0 − 0 + 0.70711×0.92388                    = +0.65328
  → q = (0.6533, −0.2706, +0.2706, 0.6533)      （模长 = 1.0000 ✓）
```

**现在换成 XYZ 顺序**（同样的三个数！）：

```
q = qx(0°) ⊗ qy(45°) ⊗ qz(90°) = qy(45°) ⊗ qz(90°)
  → q = (0.6533, +0.2706, +0.2706, 0.6533)
```

**差别只有 x 的符号**。两个姿态差多少度？

```
两姿态夹角 = 2·arccos(|q1·q2|)
q1·q2 = 0.6533² + (−0.2706)(+0.2706) + 0.2706² + 0.6533²
      = 0.4268 − 0.0732 + 0.0732 + 0.4268 = 0.8536
夹角 = 2 × arccos(0.8536) = 2 × 31.4° = 62.8°
```

> **同样的三个数字 `(90, 45, 0)`，只因为乘的顺序不同，最终姿态相差 62.8°。**
> 在云台上就是"枪管朝左上方 45°"变成"朝右上方 45°" —— 差出一条街。
> **这就是"欧拉角必须带顺序"的含义；四元数本身没有顺序问题（它直接给最终旋转），但"从欧拉角转成四元数"这一步有。**

### 2.3.4 四元数乘法（Hamilton 积）

两个四元数 `p = (pw, px, py, pz)`、`q = (qw, qx, qy, qz)`：

```
p ⊗ q = ( pw·qw − px·qx − py·qy − pz·qz,
          pw·qx + px·qw + py·qz − pz·qy,
          pw·qy − px·qz + py·qw + pz·qx,
          pw·qz + px·qy − py·qx + pz·qw )
```

**物理意义**：`p ⊗ q` = **先做 q，再做 p**（两个旋转都表达在**同一个固定坐标系/世界系**里）。

- ⚠️ 顺序不能交换：`p ⊗ q ≠ q ⊗ p`（转 90° 再转 45° 和反过来，结果不同）。
- 若两个旋转都相对于**机体自身**的轴（内旋），顺序要反过来写 `q ⊗ p`。**这是实践中最常错的一处**。

**工程里现成的例子**（`gimbal.c` L450–453，1.3.2 已展开验证过）：`q_out = q_rot(−bias) ⊗ q_in` —— 左乘 = 在世界系里再转一次，所以是"把姿态整体绕世界 Z 轴倒转 bias 角度"，正好对应 `yaw − bias_accum`。

### 2.3.5 ★ 归一化：为什么必须 \|q\| = 1

四元数只有**单位长度**时才表示"纯旋转"。若 `|q| = 1.02`，用标准公式算出的旋转矩阵：

```
R = [1−2(y²+z²)      2(xy−wz)      2(xz+wy) ]
    [2(xy+wz)    1−2(x²+z²)        2(yz−wx) ]
    [2(xz−wy)      2(yz+wx)    1−2(x²+y²)  ]
```

每一项都是 q 的**二次型** → 整个 R 被放大 **|q|² = 1.02² = 1.0404（+4.04%）**。

**具体后果**：视觉拿这个 q 去旋转"目标向量"（例如 10 m 远处、方向正确）：

```
|R·v| = 1.0404 × |v|  →  10.00 m 变成 10.40 m
```

→ 弹道解算按 10.4 m 算，**距离错 0.4 m**；同时 R 不再是正交阵，反解出的欧拉角也会有零点几度的偏差。

> **"1.02 放大 2%" 这个说法要修一下**：|q| 本身就是 1.02（+2%），但 R 里是 q 的平方，误差是 **+4.04%**。
> **修法只有一个**：`q ← q / √(w²+x²+y²+z²)`（即 `\|q\|` 归一化），一步就消掉。EKF 内部每拍都做（`user_quaternion_ekf.c` L240–244）。

归一化的代价：1 kHz × 4 次乘法 + 1 次开方。本工程用 `invSqrt()`（快速反平方根）省时间。

### 2.3.6 共轭 `q*` 与反向旋转

```
q* = (w, −x, −y, −z)
```

对单位四元数：**`q* = q⁻¹`**（逆），作用就是**反向旋转**（θ → −θ）。

**验证**（用 2.3.2 的 30° 例子）：

```
q  = (0.96593, 0, 0, 0.25882)     绕 Z 转 +30°
q* = (0.96593, 0, 0, −0.25882)    绕 Z 转 −30°

q ⊗ q*:  w = 0.96593² − 0 − 0 − 0.25882×(−0.25882) = 0.93303 + 0.06699 = 1.00002 ≈ 1
         z = 0.96593×(−0.25882) + 0.25882×0.96593   = −0.25000 + 0.25000 = 0
→ q ⊗ q* = (1, 0, 0, 0)   ✓ 单位四元数 = 没有旋转
```

**工程里的用法**：坐标变换的反向（世界→机体 / 机体→世界）、误差四元数 `q_err = q_target ⊗ q_current*`（`q_err` 的旋转轴就是"该往哪边转"）。

### 2.3.7 单位四元数 `q = (1,0,0,0)` 表示什么

**"转 0°，什么都不做"**。因为 `θ=0` → `w = cos0 = 1`，`sin0 = 0`。

**为什么代码里一定要显式初始化它**（`attitude.c` L35–38、`user_vision.c` L60–63）：

- 若发 `(0,0,0,0)`：`|q| = 0` → 归一化除零 → 视觉解出 **NaN** → 它建的坐标系全废；
- BSS 清零的全局结构体**天然就是 (0,0,0,0)**，所以必须显式写 `q[0] = 1.0f`；
- 代码注释原话："`绝不能发 (0,0,0,0)` —— 那不是合法四元数，视觉解出来会是 NaN"。

### 2.3.8 从四元数反解欧拉角（本项目 QEKF 的"轴交换"在这里）

标准 ZYX 反解（`q = w + xi + yj + zk`）：

```
yaw   ψ = atan2( 2(wz + xy), 1 − 2(y² + z²) )
pitch θ = asin ( 2(wy − zx) )
roll  φ = atan2( 2(wx + yz), 1 − 2(x² + y²) )
```

对照 `user_quaternion_ekf.c` L205–207：

| 代码变量 | 代码公式 | 对照 | 真正的物理意义 |
|---|---|---|---|
| `QEKF_INS.Yaw` | `atan2(2(q0q3+q1q2), 2(q0²+q1²)−1)` | `2(q0²+q1²)−1 = 1−2(q2²+q3²)` | ψ ✅ 正确 |
| `QEKF_INS.Pitch` | `atan2(2(q0q1+q2q3), 2(q0²+q3²)−1)` | `2(q0²+q3²)−1 = 1−2(q1²+q2²)` | **φ（roll）** ❌ 名字错 |
| `QEKF_INS.Roll` | `asin(−2(q1q3−q0q2))` | `= asin(2(q0q2−q1q3))` | **θ（pitch）** ❌ 名字错 |

**结论**：这个 EKF 的 `Roll` / `Pitch` 两个名字**互换了**。所以：

- 发给视觉的 `pitch` 用 `qe_roll`（`gimbal.c` L427）；
- 如果你想在串口上看真实俯仰，看 `qe_roll`，**别看 `qe_pitch`**；
- `qe_yaw` 是可信的 yaw（但云台闭环用的是 `Attitude_Get_Yaw()`，即互补滤波/积分的 yaw，两个 yaw 会缓慢分离，因为 EKF 的 z 轴零偏**被强制为 0**，见 2.4.3）。

> **这不是"参考工程的 bug"，是参考工程的命名习惯**：`dvc_bmi088.cpp` 里明确写了 `Data_Euler.pitch = QEKF_INS.Roll`。跨工程抄代码时**必须连名字一起核对**，否则 2.6.4 那种 bug 迟早出现。

## 2.4 IMU 六轴与姿态解算

### 2.4.1 陀螺仪：测角速度 → 积分 → **会漂**

- 陀螺输出是**角速度**（BMI088 原始单位 rad/s）。
- 要得到角度只能**积分**：`θ += ω·dt`。
- 积分会把**任何恒定小偏差**累积成线性漂移：

```
漂移角(°) = 零偏(°/s) × 时间(s)
```

★ **数字例子**（用 `gimbal.h` L113 记录的实测零偏 0.05 °/s）：

| 时间 | 漂移角 |
|---:|---:|
| 10 s | 0.5° |
| **1 min** | **3.0°** |
| 5 min | 15° |
| **10 min** | **30°** |

如果零偏只有 0.03 °/s（题面给的量级）：1 min → **1.8°**，10 min → **18°**。
**结论：裸积分的 yaw 十分钟就能漂掉一整个装甲板的宽度**，必须做零偏估计（2.5）或外部参考（磁力计/视觉）。

### 2.4.2 加速度计：测重力 → **pitch/roll 有绝对参考**

静止时加速度计测到的是"重力反作用力"方向（往上 1 g）。由它可以算出**相对水平的倾角**，而且**不随时间漂**：

```c
/* attitude.c L97：俯仰 = atan2(−ax, √(ay² + az²)) */
pitch_acc = atan2f(-ax, sqrtf(ay*ay + az*az)) * RAD2DEG;
```

★ **数字例子**：IMU 抬头 30°，静止（g = 9.80665 m/s²）：

```
ax = −g·sin(30°) = −4.9033
ay = 0
az = +g·cos(30°) = +8.4928

pitch_acc = atan2(4.9033, √(0 + 8.4928²)) = atan2(4.9033, 8.4928)
          = 0.5236 rad = 30.000°   ✓
```

**局限**：只在**静止或准静止**时准。一旦有水平加速度（车在跑、被撞），`ax` 里混进运动加速度，算出的角度就错 —— 所以它只能**慢速**修正（互补滤波 τ=1 s，见 2.5.1）。

### 2.4.3 ★ 为什么 yaw **一定**漂

**核心事实**：绕重力轴（世界 Z）旋转**不改变重力方向**。

★ **数字例子**：同一块板，先 yaw=0°，再 yaw=90°，静止时加速度计读数：

| 姿态 | ax | ay | az | 加速度计能看出区别吗 |
|---|---:|---:|---:|---|
| yaw = 0°, pitch = 0° | 0 | 0 | 9.8067 | — |
| yaw = 90°, pitch = 0° | 0 | 0 | 9.8067 | **完全一样** |
| yaw = 任意角, pitch = 0° | 0 | 0 | 9.8067 | **完全一样** |

→ **加速度计对 yaw 完全无感**。6 轴 IMU 没有磁力计（不能用地球磁场做第二个参考）→ **yaw 的绝对参考不存在** → 只能靠陀螺积分 → 必然漂。

**代码里的铁证**（`user_quaternion_ekf.c` L200–202）：

```c
QEKF_INS.GyroBias[0] = FilteredValue[4];
QEKF_INS.GyroBias[1] = FilteredValue[5];
QEKF_INS.GyroBias[2] = 0;   /* ← 注释：大部分时候z轴通天,无法观测yaw的漂移 */
```

EKF 只估计 **x/y 两轴**的零偏，**z 轴零偏被强制写 0** —— 因为量测（重力方向）里根本不含 z 轴信息，估不出来。

**三重后果（本项目全部命中）**：

1. `Attitude_Get_Yaw()` 是**纯陀螺积分**（`attitude.c` L105–110：`yaw_gyro += yaw_rate·dt`，互补滤波只融合了 pitch）。
2. 位置环去追这个会漂的 yaw → 静止时"每 5~6 秒飘一下/慢慢抖"（`gimbal.h` L112–116 的实测描述）。
3. 所以必须有 `bias_accum` 机制（2.5.3）。

## 2.5 EKF / 互补滤波在做什么

### 2.5.1 互补滤波（本工程真正提供 pitch 绝对基准的那一环）

```c
/* user_cf.c 的一阶互补滤波；参数 ATTITUDE_CF_TC = 1.0 s，dt = 1 ms */
pitch = pitch_gyro + α·(pitch_acc − pitch_gyro),   α = dt/(τ+dt) = 0.001/1.001 = 0.000999
```

**它做的事**：**相信陀螺的短时动态，相信加速度计的长期绝对基准**。

★ **数字例子**：陀螺积分说 31.0°、加速度计说 30.0°（差 1°），τ = 1 s：

| 经过时间 | 修正量 | 输出 | 剩余误差 |
|---:|---:|---:|---:|
| 1 拍 (1 ms) | 1° × 0.001 = 0.001° | 30.999° | 0.999° |
| 1 s | 1° × (1−e⁻¹) = 0.632° | 30.368° | 0.368° |
| 3 s | 1° × (1−e⁻³) = 0.950° | 30.050° | 0.050° |
| 5 s | 1° × 99.3% | 30.007° | 0.007° |

→ **1 s 修 63%，3 s 修 95%**。τ 越大越"信陀螺"（抗震动、但零偏暴露得越久）；本工程取 1.0 s。

⚠️ **注意**：`attitude.c` 只对 **pitch** 做了互补滤波；**roll 没算，yaw 纯积分**。所以"pitch/roll 不漂"这句话在本工程里准确讲是"**pitch 不漂，roll 没实现**"。

### 2.5.2 四元数 EKF（`ATTITUDE_EKF_ENABLE = 1`）

| 项目 | 值 | 出处 |
|---|---|---|
| 状态维数 | **6**：q(4) + gyro bias x/y(2) | `Kalman_Filter_Init_Static_6_0_3` |
| 量测 | 3 维：归一化加速度（重力方向） | `MeasuredVector[3]` |
| `Q1`（四元数过程噪声） | 10.0 | `attitude.c` L46 |
| `Q2`（零偏过程噪声） | 0.001 | 同上 |
| `R`（加速度量测噪声） | **1e7**（单位 (m/s²)²） | 同上 |
| `lambda`（渐消因子） | 1.0（不渐消） | 同上 |
| 加速度低通 `lpf` | 0（关闭） | 同上 |
| 静止判据 | `\|gyro\| < 0.3 rad/s` 且 `9.3 < \|acc\| < 10.3 m/s²` | `user_quaternion_ekf.c` L172 |
| 卡方检验阈值 | 1e-8 | L55 |

**它输出什么**：`q[4]`（给视觉）、`GyroBias[0..1]`（x/y 零偏）、`Yaw/Pitch/Roll`（轴交换过的欧拉角，见 2.3.8）。

**`R = 1e7` 意味着什么**：量测噪声被设得极大 → 卡尔曼增益极小 → **EKF 几乎完全相信陀螺**，加速度只做极慢的微调。这与参考工程同量级（参考默认 1e6），不是笔误；但工程含义要清楚：

> **不要指望 EKF 帮你稳住 pitch/roll**。本工程 pitch 的绝对基准实际来自互补滤波（2.5.1），EKF 的主要价值是**给出四元数**和**x/y 零偏估计**。
> 想让 EKF 真正参与姿态修正，`R` 要降到 1e2~1e3 量级，**但这会显著改变动态特性，必须重测**（`待整定`，附录 B #3）。

### 2.5.3 `bias_accum` 是什么，为什么能减漂

`gimbal.h` L112–130 + `gimbal.c` L473–494。三段式：

**① 零偏的"观测"**（L482–487）：只在**摇杆居中 + 编码器说云台没动**时才更新

```c
if (bias_k > 0 && stick == 0 && |enc_rate_lpf| < 0.5 deg/s) {
    yaw_bias += bias_k * (user_attitude.yaw_rate - yaw_bias);   /* 一阶低通 */
}
```

- `bias_k = GIMBAL_BIAS_TRACK_ALPHA = 0.0002`，1 kHz → **τ = 1/(α·1000) = 5 s**。
- 逻辑：云台**物理上没动** → 真实角速度 = 0 → 此时陀螺测到的 `yaw_rate` **就是零偏**。

**② 累积成角度**（L488）：

```c
bias_accum += yaw_bias * GIMBAL_DT_S;      /* 0.001 s */
```

零偏 0.05 °/s → `bias_accum` 每秒涨 0.05°。

**③ 从反馈里减掉**（L514）：

```c
world_yaw = Wrap180(imu_yaw - bias_accum);   /* 位置环用这个 */
```

★ **为什么这样就能"治住"漂移**：

- 不扣的后果：`imu_yaw` 以 0.05 °/s 自增 → 位置环看到"我偏了" → 命令云台**物理上反向爬行**去追 → 就是"每 5~6 秒飘一下"。
- 扣掉之后：`world_yaw` 不再自增 → 位置环不需要爬 → 云台**真的停住**，而且位置环可以保持满刚度（死区缩到 0.05°）。

**为什么标定必须在"温度稳定 + 静止"时做**（`gimbal.h` L132–148）：

- 零偏**随温度变**（2.8）：冷机 → 热机的零偏差可以达到 0.1~0.5 °/s 量级，而在线跟踪 τ=5 s 只能慢慢追；
- 采样窗口里云台一动，`yaw_rate` 里就混进真实角速度 → 标出来的"零偏"是错的；
- 所以流程被设计成：**加热到 47℃（`preheat_done`）→ 静止连续 200 ms → 采 2 s → 平均写入 `yaw_bias`**（`GIMBAL_CALIB_MS = 2000`、`GIMBAL_CALIB_STABLE_MS = 200`、`GIMBAL_CALIB_TIMEOUT_MS = 10000`）。

**平均能压多少噪声**（为什么 2 s 就够）：BMI088 静止噪声约 0.1~0.2 °/s rms（`gimbal.h` L144–146）。2 s = 2000 个样本：

```
噪声从 0.2 °/s → 0.2/√2000 = 0.0045 °/s
残余漂移：0.0045 × 60 = 0.27 °/min，10 min 2.7°
（不标定：0.05 °/s → 3 °/min → 10 min 30°，差 11 倍）
```

> 顺便解释 `GIMBAL_CALIB_GYRO_MAX_DPS = 1.0` 这个阈值：0.1~0.2 °/s 的噪声是 5~10σ 之外，所以 1.0 既不会把噪声当"在动"，又能挡住手碰/转底盘。

## 2.6 坐标系（★ 本文核心）

### 2.6.1 五个坐标系，各自的定义

| 坐标系 | 符号 | 原点/轴向 | 本工程的量 | 参考系 |
|---|---|---|---|---|
| **世界系** | W | Z 轴竖直向上，X/Y 水平；yaw 绕 Z | `target_yaw`、`yaw_fb`、`imu_yaw − bias_accum` | 绝对（但 yaw 原点由 `yaw_offset` 任意定） |
| **云台 yaw 框架系** | G | 与云台 yaw 轴固连；**C 板的 BMI088 就装在这里** | `imu_yaw`、`user_attitude.yaw` | 与 W 只差一个 yaw |
| **云台 pitch / 枪管系** | P | 与 pitch 轴固连，跟枪管一起俯仰 | `gimbal->pitch`（**关节角**）、`pitch_speed` | 与 G 只差一个 pitch |
| **相机系** | C | 光轴 = 相机 Z；装在上方/侧面，有安装偏差 | `cam_yaw_off`、`cam_pitch_off` 描述它和 P 的差 | 与 P 固定 |
| **底盘系** | B | 与底盘固连 | `gimbal->yaw`（**相对底盘**）、`user_chassis.omega` | 与 W 差底盘朝向 |

**层级关系（一句话）**：

```
B（底盘）──yaw 电机── G（yaw 框架，IMU 在这）──pitch 电机── P（枪管/相机）
                                        ↑
                            视觉给的是"世界系 W 下的目标方向"
```

### 2.6.2 ★ 同一个物理方向，在各坐标系里的数值完全不同

**场景**：1 m 外、正前方、比枪管**低 10°** 的装甲板中心。几何真值：世界仰角 = **−10.0°**。

| 坐标系 / 量 | 数值 | 怎么来的 |
|---|---:|---|
| 世界系仰角 | **−10.00°** | 几何真值（水平为 0，上为正） |
| 相机系（光轴基准） | −10.00° − 安装倾角 | 安装倾角折进 `cam_pitch_off`（标定值，`待实测`） |
| **视觉包内 `pitch`（rad）** | **+0.17453**（若"正=下"）或 −0.17453（若"正=上"） | 取决于视觉的符号约定（**`待确认`**，见附录 B #1） |
| **云台关节角（要打过去的目标）** | **9.1403 − 10.00 = −0.86°** | 关节 0° = 水平下方 9.1403°（2.6.3） |
| **电机绝对编码器角** | **−0.86 + 90.5716 = 89.7116°** | 绝对角 = 关节角 + 90.5716 |
| 相对软限位的位置 | −0.86 在 [−10.8, +28.6] 内，**距下极限 9.94°** | `GIMBAL_PITCH_MIN_DEG` |
| 编码器计数（GM6020，8192/圈） | 89.7116 / 0.043945 ≈ **2041.4 count** | 360/8192 = 0.043945°/count |

> **同一个方向，7 个数字**：−10 / −10 / +0.17453 / −0.86 / 89.71 / 9.94 / 2041。
> **看错任何一个的"基准"，枪口就偏 9.14°（1 m 处偏 16 cm，5 m 处偏 80 cm）。**

### 2.6.3 本项目的具体约定（必背）

| 量 | 类型 | 零点 | 正方向 | 范围 |
|---|---|---|---|---|
| `gimbal->pitch` | **关节角** | 绝对编码器 90.5716°（`GIMBAL_PITCH_ABS_TO_JOINT_OFFSET`） | 增大 = **向后仰（上抬）** | 软限位 **−10.8 ~ +28.6°** |
| `gimbal->target_pitch` | 关节角目标 | 同上 | 同上 | 每拍被 `Gimbal_Clamp_Pitch_Target()` 夹住 |
| **水平姿态** | 关节角 | — | — | **+9.1403°**（`GIMBAL_PITCH_BOOT_TARGET_DEG`） |
| `gimbal->yaw` | **相对底盘**的编码器角 | `zero_deg`（上电对齐时写） | `GIMBAL_YAW_DIR = +1`（待现场核对） | ±180° |
| `gimbal->yaw_fb` | **世界角**（IMU） | IMU 上电时的 yaw | IMU 积分方向 | ±180° |
| `gimbal->imu_yaw` | 世界角 | 同上 | 同上 | ±180° |
| 视觉 `target_yaw` | 世界角（**覆盖式**） | 与 `yaw_fb` 同基准 | 同 IMU | ±180° |

**关节角↔绝对角的换算（唯一公式）**：

```
关节角 = 绝对单圈编码器角 − 90.5716°
绝对角 = 关节角 + 90.5716°
```

**实测锚点**（`gimbal.h` L282–296 的用户实测数据）：

| 位置 | 绝对单圈角 | 换算关节角 | 对应软限位 |
|---|---:|---:|---|
| 枪管最上（仰到底） | 120.718° | **+30.146°** | 上限 +28.6°（留 1.5° 余量） |
| 上电水平 | 99.7119° | **+9.1403°** | 回位目标 |
| 枪管最下（俯到底） | 78.2606° | **−12.311°** | 下限 −10.8°（留 1.5° 余量） |

→ 机械行程 **−12.311 ~ +30.146°**，软限位 **−10.8 ~ +28.6°**，两端各留 1.5° 安全余量。
→ 绝对角对应：**79.7716°（下） ~ 119.1716°（上）**。

**为什么关节零点这么怪**：GM6020 的绝对单圈编码器零位是**装机械时随机定下的**，`99.7119°` 那一点恰好是枪管水平。为了不改电机零位，用"减一个常量"的方式把绝对角搬到"以水平为 9.1403°"的关节系上。**这个 9.1403 不是标定误差，是一个刻意的"重力偏置"。**

### 2.6.4 ★ 2026-10-25 实战 bug：视觉 pitch 被当成关节角用

#### 现象

> 目标**越近**，云台**越往上抬**；应该在近距离下压。距离越近偏差越大。

#### 数据（1.5.2 那包数据就是现场形态）

| 距离 | 视觉发的 `pitch`（rad / deg） | 几何真值（世界仰角） | 应给的关节角 |
|---:|---|---:|---:|
| 5 m | 0.05236 / **+3°** | −3° | **9.1403 − 3 = +6.14°** |
| 3 m | 0.10472 / **+6°** | −6° | **9.1403 − 6 = +3.14°** |
| 1 m | 0.17453 / **+10°** | −10° | **9.1403 − 10 = −0.86°** |

#### 推理：代码实际算的是什么

`gimbal.c` L1040：

```c
const float pitch_ext = raw_pitch * VISION_PKG2DEG + gimbal->cam_pitch_off;
/*                     = 10.0            + 3.0   = 13.0°（关节角域） */
```

**这一行做了两件事，偏偏漏了最关键的第三件**：

| 应该做 | 代码 | 后果 |
|---|---|---|
| ① 加**关节零点基准** 9.1403°（视觉说的是"相对水平"，关节角说的是"相对编码器零位"） | ❌ **没有** | 整体偏 9.14° |
| ② 乘**方向符号** −1（视觉 pitch 正 = 向下，云台关节角正 = 向上） | ❌ **没有**（`GIMBAL_VISION_PITCH_SIGN` 定义了但全工程没人引用） | 方向完全反 |
| ③ 加 `cam_pitch_off`（光轴/枪管不同轴的固定偏置） | ✅ 有，+3.0 | 这只能补常量，补不了①② |

**代入 1 m 的数据**：

| | 目标关节角 | 关节角−水平 | 物理含义 | 1 m 处落点 |
|---|---:|---:|---|---|
| **正确** | −0.86° | −10.00° | 枪口朝下 10° | 打中 |
| **现状** | +13.00° | **+3.86°** | 枪口朝**上** 3.86° | **打高 24 cm** |
| 误差 | 13.86° | 13.86° | — | tan(13.86°)×1 m = **0.247 m** |

**"越近越上抬"的机制就清楚了**：目标越近，俯角 |pitch| 越大 → 视觉给的正值越大 → 代码算出的关节角**越大** → 枪管越往上抬。**符号反了，所以距离和方向的关系整个反转。**

3 m 时：正确 +3.14°，现状 +9.0°（6+3）→ 差 5.86° → 3 m 处偏 **0.31 m**。

#### 结论与两种正确做法

**做法 A（推荐，电控侧改）**：在 `Gimbal_Aim_Accept_Frame` 里把基准和符号都补上

```c
/* 语义：视觉 pitch = 目标相对【水平】的俯角，正 = 下（由 GIMBAL_VISION_PITCH_SIGN = −1 表达） */
const float pitch_ext = GIMBAL_PITCH_BOOT_TARGET_DEG          /* +9.1403：水平在关节系的坐标 */
                      + GIMBAL_VISION_PITCH_SIGN * raw_pitch * VISION_PKG2DEG
                      + gimbal->cam_pitch_off;
/* 例：9.1403 + (−1)(10.0) + 3.0 = 2.1403°  ← cam_pitch_off 需重标，见下 */
```

> ⚠️ **`cam_pitch_off = 3.0` 必须重新标定**。它是在**错误公式**下试出来的（`gimbal.h` L73 "实测标定：准心与装甲板同高度"），很可能吸收了 ① 缺失的一部分基准。改对公式后旧值**不再有效**，必须在靶道上重标（流程见附录 C）。

**做法 B（视觉侧改）**：让视觉**直接输出关节角**。但这要求我们回传的 `pitch` 就是关节角 —— 而当前回传的是 IMU 世界俯仰（`VISION_PITCH_USE_IMU_ONLY = 1`），**视觉无从知道 9.1403 这个零点**。所以做法 B 必须同时改回传字段，**两边一起改**，风险更大。

**顺便解释了另一个"怪现象"**：闸④（pitch 量程）用 `GIMBAL_PITCH_MIN/MAX_DEG`（关节角域）去卡一个"世界仰角"值 —— 两个坐标系在比大小。现在能过是因为范围宽（−11.8~29.6°），**纯属巧合**。修好公式后这条闸才真正有意义。

## 2.7 云台控制环

### 2.7.1 级联结构

**yaw（本工程）**：

```
target_yaw(世界,deg) ──► [位置环 P+阻尼] ──► target_speed(RPM) ──► [GM6020 内部速度环] ──► 电流 ──► 力矩
                          gimbal.c @1kHz        Rotor_speed 模式      电机固件 @1kHz      ±16384
```

**pitch 的串级（`GIMBAL_PITCH_CASCADE = 1`，两个 PID 跑在电机侧）**：

```
target_pitch(关节角,deg) ──► [外环角度 PID] ──► 转速目标(RPM) ──► [内环速度 PID] ──► 电流 ──► 力矩
                              kp=12 ki=2 kd=0.2     ≤200 RPM        kp=30 ki=300 kd=0
                              Rotor_angle 模式（只喂目标角）
```

**为什么 pitch 要串级**：位置环输出的是"转速"，而**顶重力需要的是恒力矩**。速度环的积分项（`ki=300`）可以在"误差 0、目标 0 RPM"时维持一个恒定的电流输出 —— 这是单环做不到的（`gimbal.h` L363–364 明确写"`ki 绝对不能是 0`：稳态时顶重力的恒力矩只能靠内环积分维持"）。

### 2.7.2 位置环 PD 各起什么作用

| 项 | 系数 | 作用 | 数学含义 | 调大的后果 |
|---|---|---|---|---|
| **P** | `world_kp = 3.2` RPM/deg | "每差 1 度给多少转速"= **弹簧刚度** | 误差 1° → 3.2 RPM = **19.2 °/s** | 越大越"想去"目标，**过大 → 振荡/过冲** |
| **D** | `world_kd = 0.95` | 用**陀螺角速度**做刹车 | 当前 1 RPM(=6 °/s) → 扣 0.95 RPM 的指令 | 越大刹车越重，**过大 → 发粘、跟手变慢** |
| **死区** | `world_dead = 0.05°` | 误差 < 0.05° 时 P 项清零 | 只清 P，**阻尼和前馈仍工作** | 越大越"稳"但会有静差 |
| 限幅 | `MAX_RPM = 150` | 只夹**修正量**，不夹前馈 | — | — |

**★ 数字例子（振荡是怎么来的）**

开环时间常数 `τ ≈ 6/world_kp`（位置环输出 RPM，1 RPM = 6 °/s）：

```
kp = 3.2  → τ = 6/3.2 = 1.875 s
kp = 3.0  → τ = 2.00 s
kp = 2.2  → τ = 2.73 s     （gimbal.h L161-163 的历史记录，与注释一致 ✓）
```

**只有 P 没有 D 时**：误差 10° → 32 RPM = 192 °/s → 云台以 192 °/s 冲向目标 → 到位时速度还是 192 °/s → **冲过头** → 反向误差又给 192 °/s 反向 → 来回摆（欠阻尼振荡）。

**加上 D（kd=0.95）**：到目标前速度 192 °/s = 32 RPM → D 项扣 0.95×32 = **30.4 RPM** 的刹车，几乎把 P 项（32 RPM）抵消掉 → **提前松油门** → 过冲被压住。

`gimbal.h` L169–173 的实测记录：`kd 0.55 → 0.85 → 0.95`，过冲逐步受控、不迟钝；**整定顺序必须是"先加 kd，再提 kp"**（反过来必振荡）。

**阻尼源的一阶低通** `world_d_alpha = 0.55`：陀螺噪声会直接进转速指令。α 大 = 滞后小、刹车早（效果好），代价是噪声进指令（"沙沙"感/发热）；α 从 0.40 提到 0.55 就是"让刹车早几十毫秒"。

### 2.7.3 ★ 速度前馈：为什么"不滞后"

**纯反馈的固有缺陷**：P 项要产生转速就必须**先有误差**。

★ **数字例子（pitch 外环，`kp = 12` RPM/deg）**：目标以 **120 °/s** 匀速移动。

| 方案 | 计算 | 稳态误差 | 手感 |
|---|---|---:|---|
| 纯 P | 需要 120/6 = **20 RPM** 的输出 → 误差 = 20/12 = **1.67°** | 1.67° | "慢半拍" |
| 加前馈 KF | `ff = KF × 目标角速度 = 0.167 × 120 = 20.04 RPM` | **0°** | 跟手 |

**为什么 0.167 是"理论最优"**：`1 RPM = 6 °/s` → 要把 120 °/s 精确换成一个转速指令，系数必须是 `1/6 = 0.1667`。`GIMBAL_PITCH_ANGLE_KF = 0.167` 就是这个精确值（`gimbal.h` L344–350）。

**前馈的三大好处**（都能在代码里对上）：

1. **零滞后**：前馈直接给"该以多快转"，不用等误差攒出来。
2. **不影响稳定性**：前馈**不在反馈回路里**（它不改变闭环特征方程），所以改它不会振荡 —— 这正是它比"加 kp"安全的原因（`gimbal.h` L61）。
3. **可以过喂**：`GIMBAL_YAW_KF = 1.30`（摇杆前馈乘 1.3）= 故意多给 30%，起步更利落；代价是松杆时"橡皮筋感"。

**★ 那为什么视觉前馈只有 0.45（而不是理论最优 1.0）？**

因为视觉的角速度是**带噪声的**：

| 值 | 语义 | 噪声进速度环的幅度 |
|---|---|---|
| 1.0（理论最优） | 完全信任视觉角速度 | ±16 °/s（`gimbal.h` L82 实测的视觉角速度噪声）→ ÷6 = **±2.7 RPM** 的指令抖动 |
| **0.45（当前）** | 只信 45% | ±16×0.45 = ±7.2 °/s → **±1.2 RPM** |
| 0（2026-10-17 曾关闭） | 完全不信 | 0，但移动目标跟不动 |

`gimbal.h` L80–84 的记录：2026-10-17 因噪声大关到 0；2026-10-24 取 0.25；**2026-10-25 取 0.45**（配合"自瞄平滑 2 ms + 外推 30 ms"）。这就是工程里的典型折中：**前馈系数 = 跟踪精度 vs 抖动 的滑块**，理论值只是上界。

> ⚠️ **注意 0.45 和 0.167 不是同一个东西**：0.167 是**单位换算**（deg/s→RPM，必须有），0.45 是**信任系数**（0~1，可调）。视觉前馈的完整算式是 `aim_rate = 0.45 × 视觉角速度`，再 `÷6` 进速度环 → 等效 `0.45/6 = 0.075 RPM per °/s`，只有理想值（0.1667）的 45%。

### 2.7.4 目标平滑与延迟的取舍

一阶低通的系数是**按 τ 现算**的（不是魔数）：

```c
alpha_s = dt / (τ + dt) = 0.001 / (0.012 + 0.001) = 0.0769   /* τ=12ms */
alpha_s = 0.001 / (0.002 + 0.001) = 0.3333                   /* τ=2ms  */
```

| 模式 | τ | α | 群延迟 ≈ τ | 目标 120 °/s 时的滞后 | 用途 |
|---|---:|---:|---:|---:|---|
| **摇杆** `GIMBAL_TGT_SMOOTH_RC_MS` | **12 ms** | 0.0769 | 12 ms | 120×0.012 = **1.44°** | 跟手优先 |
| **自瞄** `GIMBAL_TGT_SMOOTH_AIM_MS` | **2 ms** | 0.3333 | 2 ms | 120×0.002 = **0.24°** | 稳 + 不抖 |

**为什么要平滑**：摇杆给的是**阶跃**目标（松杆瞬间目标角直接"折"住），阶跃里含全频段能量 → 位置环必过冲。一阶低通把折角磨圆，位置环从"救火"变成"跟随"（`gimbal.h` L211–230 有完整推导）。

**为什么自瞄反而要"小 τ"**：视觉 100 Hz 更新，每帧目标**已经**是台阶。τ 太大会把台阶磨成明显的斜坡 → 移动目标跟不上。所以取 2 ms（只削尖峰，不引入明显滞后）。

**延迟外推**（`GIMBAL_AIM_DELAY_MS = 30`）：视觉看到的是**过去**，用云台自身角速度线性外推到"现在"：

```c
target_pitch = pitch_target_ext + pitch_speed×6 × (30/1000)     /* L910-912 */
target_yaw   = yaw_target_ext   + yaw_rate_lpf×6 × (30/1000)    /* L361-363 */
```

★ **数字例子**：

| 云台角速度 | 30 ms 外推量 | 说明 |
|---:|---:|---|
| 30 °/s | 0.90° | 低速时几乎无影响 |
| 60 °/s | **1.80°** | 明显改善跟踪滞后 |
| 120 °/s | **3.60°** | 高速横移的关键 |
| 171.9 °/s（满杆） | 5.16° | 外推过大时会"提前到位" |

**外推的代价**：目标**换向**时，线性外推会往旧方向多冲一段：

```
目标加速度 500 °/s²，外推 30 ms 的误差 = ½·a·t² = ½×500×0.0009 = 0.225°
```

→ 可控。所以 30 ms 是个不错的折中；`gimbal.h` L87–88 记录"原 20，实测 30 更贴合真实滞后"。

> ⚠️ **两个外推项用的是不同的速度源**：yaw 用 `yaw_rate_lpf`（IMU 陀螺），pitch 用 `pitch_speed`（电机转速）。前者是**世界系物理角速度**，后者是**关节角速度**（在 yaw 框架倾斜时代数上不相等）。小角度/小 pitch 时差别可忽略，**大 pitch 时会引入误差**（`待确认`量级）。

### 2.7.5 延迟预算表（自己心里要有一本账）

| 环节 | 延迟 | 出处 |
|---|---:|---|
| 视觉帧周期 | 10 ms（100 Hz）→ 平均半帧 5 ms | `VISION_TX_PERIOD_MS` 同量级 |
| 串口传输 29 B | 2.52 ms | 115200 8N1 |

## 2.8 零偏与温漂

### 2.8.1 零偏随温度变

MEMS 陀螺的零偏对温度敏感。**加热到 47℃ 再标定，是为了让"标定时的温度"和"工作时的温度"一致**：

- 冷机标定（25℃）→ 工作到 47℃ → 零偏漂了 → `imu_yaw` 又开始跑；
- 但工程的在线跟踪（τ=5 s）会慢慢追上 → 表现为"上电头几分钟慢慢偏、后面稳住"；
- 所以流程改成：**先满占空比加热到 47℃（`HEATER_PREHEAT_DUTY`）→ 切 PID 恒温 50℃（`HEATER_TARGET_TEMP_DEF`）→ 再标定**。

| 参数 | 值 | 出处 |
|---|---:|---|
| 预热结束阈值 | **47.0℃** | `HEATER_PREHEAT_BASE_TEMP_DEF` |
| 恒温目标 | **50.0℃** | `HEATER_TARGET_TEMP_DEF` |
| 过温保护 | 65℃（回差 5℃） | `HEATER_OVER_TEMP` |
| 加热控制周期 | 100 ms | `HEATER_PERIOD_MS` |

**温漂量级**（`待确认`：需查 BMI088 手册 + 实测）：若零偏温漂在 0.01~0.03 °/s/℃ 量级，则 25℃ → 47℃ 变化 22℃ 会带来 **0.22~0.66 °/s** 的零偏变化 = **13~40 °/min** 的漂移。**这就是"为什么必须恒温 + 稳温后标定"**的定量理由。

> ⚠️ 注意 `gimbal.h` 里有两个**差 30 倍**的零偏数字：L9 注释"实测 625S 左右零飘偏一度（10分钟）"≈ 0.0016 °/s，而 L113 写"实测约 0.05deg/s"。两者不可能同时是"同一次测量"。**列为待确认（附录 B #6）**，本文的漂移算例用 0.05 °/s（更保守），并用 0.0016 °/s 代表"标定+在线跟踪之后的残余"。

### 2.8.2 静态标定流程（按代码状态机）

```
IDLE  ──(预热到 47℃ / 或 heater.enabled==0 跳过)──►  WAIT
WAIT  ──(静止条件连续 200 ms)──►  COLLECTING
COLLECTING ──(采满 calib_ms = 2000 ms)──► DONE：yaw_bias = 均值；bias_accum = 0
COLLECTING ──(静止被破坏 / 掉线)──► 回 WAIT（清空重来）
WAIT/COLLECTING ──(从加热就绪起 10 s 没成功)──► TIMEOUT（放弃，靠在线跟踪兜底）
```

**"静止"的四个条件**（`gimbal.c` L649–656，全部满足才算）：

| # | 条件 | 阈值 |
|---:|---|---|
| ① | 加热就绪 | `preheat_done != 0` 或 `heater.enabled == 0` |
| ② | 云台在线且已对齐 | `is_online && is_aligned` |
| ③ | IMU 在线且完成自身标定 | `bmi088.is_online && bmi088.calibrated` |
| ④ | **静止** | `stick == 0` **且** `\|enc_rate_lpf\| < 0.5 °/s` **且** `\|gyro_z\| < 1.0 °/s` |

**关键设计（别踩）**：DONE / TIMEOUT 是**终态**，不会自己重来（否则每次摇杆回中都会重标一遍）。要重标只能写在线调参 `calib_restart = 1`。

**标定完成后做了什么**（L782–789，注意顺序）：

```c
target_yaw       += old_accum;      /* ★ 目标角的基准一起平移，避免标定瞬间云台甩一下 */
target_yaw_smooth += old_accum;
yaw_target_ext   += old_accum;
yaw_bias    = avg;                  /* 新零偏 */
bias_accum  = 0.0f;                 /* 从零重新积分 */
```

**为什么要把三个目标角各加 `old_accum`**：`bias_accum` 从 A 突然变 0，等价于世界系基准整体平移了 A。若不移目标，`(目标 − 反馈)` 会瞬间多出 A 度的误差 → 云台猛甩。平移目标即保证 `(T_new − W_new) == (T_old − W_old)`（L780–781 的推导）。

## 2.9 视差（相机与枪管不同轴）

### 2.9.1 公式

相机与枪管轴线有横向/纵向偏移 `d`，目标距离 `L`，则视觉看到的方向与枪管实际需要指向的方向差：

```
Δθ = atan(d / L)        （弧度）   →  Δθ_deg = atan(d/L) × 57.29578
```

**关键性质**：**Δθ 随 L 变化，不是常量**。所以任何**固定**的 `cam_offset` 只能在一个距离上准确。

### 2.9.2 ★ 数字表（偏移 3 / 5 / 10 cm 在 1 / 3 / 5 / 10 m 的角度误差）

| 偏移 `d` | 1 m | 3 m | 5 m | 10 m |
|---:|---:|---:|---:|---:|
| **3 cm** | 1.718° | 0.573° | 0.344° | 0.172° |
| **5 cm** | 2.862° | 0.955° | 0.573° | 0.286° |
| **10 cm** | 5.711° | 1.910° | 1.145° | 0.573° |

（`Δθ = atan(d/L)`，例：`atan(0.05/3) = 0.01665 rad = 0.955°`）

### 2.9.3 为什么"固定 cam_offset 只能在一个距离对"

假设相机比枪管低 **5 cm**，我们在 **3 m** 处打靶把 `cam_pitch_off` 标定好（吸收 0.955°）：

| 距离 | 真实视差 | 固定 offset 补偿 | **残差** | 落点偏差 |
|---:|---:|---:|---:|---:|
| 1 m | 2.862° | 0.955° | **1.907°** | **3.3 cm** |
| 3 m | 0.955° | 0.955° | 0° | 0 ✅ |
| 5 m | 0.573° | 0.955° | −0.382° | 3.3 cm（反方向） |
| 10 m | 0.286° | 0.955° | **−0.669°** | **11.7 cm** |

（落点 = `L · tan(残差)`：1×tan(1.907°) = 0.0333 m；10×tan(0.669°) = 0.1168 m）

**所以**：

1. **近距离最伤**（1 m 处 5 cm 偏移就有 2.86°，相当于半个装甲板的宽度）；
2. **10 m 处变成反向偏差**（offset 补过头）；
3. 本车的 `cam_yaw_off = −10.0°` / `cam_pitch_off = +3.0°` 是**打靶标定出来的综合常量**，只在标定距离最优（`gimbal.h` L72–73 "准心水平居中 / 准心与装甲板同高度"）。

### 2.9.4 正确做法（三选一，按代价排）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 机械** | 相机尽量与枪管同轴/最小基线（本车 5 cm 以内） | 装车空间 |
| **B. 视觉侧补偿** | 视觉知道云台关节角 + 相机外参 → 自己做三角变换 | 视觉要收到**可信的关节角**（这正是回传 `q` / `pitch` / `yaw` 的用途） |
| **C. 电控侧近似** | `offset = atan(d/L)` 随距离变，需要视觉给距离 | 本工程**没做**，因为视觉协议里**没有距离字段** |

> **注意**：协议 29 字节里**没有"距离"**，也没有"目标 ID / 跟踪状态"。所以电控**无法**做距离相关的视差补偿，只能靠 A 或 B。如果以后要加，**新增字段必须改帧长 → 两边同时改**（没有版本号字段，这点很危险）。

# 附录 C　上电自检清单（照着做，5 分钟排掉 90% 的问题）

1. **串口通不通**：串口助手 HEX 模式，115200，应该每 10 ms 看到一帧 `41 41 ...` 共 43 字节。
2. **CRC 对不对**：把收到的 43 字节里前 41 字节算 MODBUS CRC，应等于最后 2 字节（小端）。不对 → CRC 参数错了。
3. **单位是度还是弧度**：枪管水平静止时，包里 `pitch` 应约 **0.00 rad**（IMU 世界俯仰 ≈ 0°）；若看到 **9.14** → 单位混了（把度当弧度发了）。同时 `gimbal->pitch`（关节角）应是 **+9.1403°** —— 两个数**本来就不一样**，别拿去互相"校正"。
4. **四元数合法**：`\|q\|` 应在 0.999~1.001；为 0 或 NaN → 初始化/归一化出问题。
5. **yaw 基准**：`yaw` 字段 × 57.29578 应与串口绘图 ch7（`yaw_fb`，度）一致，差不应超过 0.1°。
6. **视觉在线**：`frame_count` 应以约 100/s 增长；`crc_error_count` 应基本不动。
7. **pitch 方向（最容易错）**：手推枪管**向上**，`pitch` 关节角应**增大**；若减小 → `GIMBAL_PITCH_DIR` 或编码器换算错。
8. **视觉 pitch 方向**：把装甲板放低，看云台是下压还是上抬（2.6.4 的 bug 就测这一条）。
9. **零偏标定**：上电等 `calib_state` 走到 3（DONE），看 `calib_gyro_std` 是否在 **0.1~0.2 °/s** 量级（BMI088 静止噪声，`gimbal.h` L144–146）；明显更大说明采样窗口里有人在碰车。
10. **静止漂移**：松杆静置 5 min，ch7 应几乎不动（残余 < 0.5°）；一直缓慢单向走 → 零偏没扣干净。
