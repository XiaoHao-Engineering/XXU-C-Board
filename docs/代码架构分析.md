## 一、架构层：软任务调度器（`user_systick.c`）

### 代码

```c
static SysTick_Task *systick_tasks[MAX_SYSTICK_TASK] = {0};
static uint8_t task_count = 0;

void SysTick_InitTask(SysTick_Task *Task, void *arg, uint32_t delay,
                      uint32_t period, TaskMode mode, SysTick_Callback callback) {
    Task->delay = delay;
    Task->period = period;
    Task->counter = 0;
    Task->state = Task_STOPPED;
    Task->callback = callback;

    systick_tasks[task_count] = Task;      /* ★ 注册到静态表 */
    task_count++;
}

void SysTick_Handle(void) {
    for (uint8_t i = 0; i < task_count; i++) {
        SysTick_Task *task = systick_tasks[i];
        if (task->state == Task_STOPPED) continue;

        task->counter++;
        if (task->counter >= task->delay) {
            task->callback((void *)task->arg);

            switch (task->mode) {
                case Task_ONCE:   task->state = Task_STOPPED; break;
                case Task_REPEAT: task->counter = 0;
                                  task->delay = task->period; break;   /* ★ */
            }
        }
    }
}
```

### ⭐⭐ 设计亮点 1：`delay` 和 `period` **复用一个变量**

```
启动阶段：  counter 从 0 数到 delay  →  "延迟多久才开始"
                    ↓ 到点后
运行阶段：  delay = period，counter 重新数 →  "多久跑一次"
```

**⇒ 用**一个**变量实现了「延迟启动 + 周期运行」两种语义，省内存又省代码。**

**典型用法（你工程里）：**

```c
SysTick_InitTask(&chassis_task, NULL, CHASSIS_PERIOD_MS, CHASSIS_PERIOD_MS,
                 Task_REPEAT, ChassisControl_Task);
/*              ↑delay=1ms          ↑period=1ms  → 立刻开始，每 1ms 一次 */

SysTick_InitTask(&LED_Blink_Task, &user_red_led, 10, 800, Task_REPEAT, ...);
/*              ↑10ms 后才开始                  ↑之后每 800ms 一次 */
```

### ⭐ 设计亮点 2：**静态表 + 注册式，不用动态内存**

```c
static SysTick_Task *systick_tasks[MAX_SYSTICK_TASK];   /* 静态指针数组 */
```

**⇒ 嵌入式系统（尤其比赛）**最忌动态内存** —— 碎片化、不确定延迟。这里用固定数组 + 计数，全是确定行为 ✓**

### ⚠️ 短板（也值得学）

| 问题 | 后果 |
|---|---|
| **回调串行执行** | 所有任务的执行时间**累加**。1kHz 下总时间 > 1ms 就崩 ⚠️ |
| **没有超时诊断** | 某个回调写慢了，你只能看到"整体变卡"，定位不到是谁 |
| `task_count` **无越界检查** | 注册超 `MAX_SYSTICK_TASK` 会静默越界写 |

**⭐⭐ 这解释了为什么 TIM2 要**单独**开一个定时器喂 JScope：**
```
SysTick 1kHz 上已经挂了：底盘(1kHz) + 云台(1kHz) + IMU(1kHz) + 电机发送(500Hz)
                              + 串口上报(100Hz) + LED(800ms)
        ↓
再往上面加 10kHz 的 JScope → 必崩
        ↓
所以单独用 TIM2 承担高频采样 ✓
```

**⇒ 教训：任务调度要"分层"，不同频率的任务别挤在一个时基上。**

## 二、BSP 层：全局实例表（`bsp.c`）

```c
/* Core/Src/bsp.c —— 所有实例集中在这里定义 */
CAN_DRIVES        user_can_1 = {0};
DJI_MOTOR_DRIVES  user_wheel_fl = {0};
PID_Controller    user_wheel_pid_fl = {0};
Chassis           user_chassis = {0};
GIMBAL_DRIVES     user_gimbal = {0};
...
```

```c
/* bsp.h —— 统一导出 */
extern CAN_DRIVES user_can_1;
extern Chassis    user_chassis;
...
```

### ⭐⭐ 为什么这么设计

**对比一下"反面教材"：**

```c
/* ❌ 每个模块各自 extern，散落各处 */
extern CAN_DRIVES user_can_1;      /* 在 motor.c */
extern CAN_DRIVES user_can_1;      /* 又要在 chassis.c */
...
```

**⇒ 集中管理的好处：**

| 好处 | 说明 |
|---|---|
| **一处定义、一处导出** | 加个实例只改 `bsp.c` + `bsp.h` |
| **应用层只 include `bsp.h`** | 不用管实例在哪 |
| **`{0}` 全零初始化** | 简洁，且状态确定 |
| **驱动层不认识实例** | `user_can.c` 不知道有 `user_can_1`，只接受指针 ✓ **真正解耦** |

**⭐⭐ 这是"依赖倒置"在 C 里的朴素实现：**
> **驱动层定义"接口"（`CAN_DRIVES` + 函数），BSP 层提供"实例"，应用层消费。**

### ⭐ 主循环事件表

```c
LOOP_Event loop_event[MAX_LOOP_EVENT] = {0};
uint8_t loop_event_num = 0;

void LOOP_EVENT_Handle(void) {
    for (uint8_t i = 0; i < loop_event_num; i++) {
        loop_event[i]();
    }
}
```

**⇒ 驱动自己"申请"进主循环（`CAN_Init` 里注册 `CAN_QueueHandle`），而不是 main 里硬编码。**

**对比：**

```c
/* ❌ 硬编码 */
while (1) {
    CAN_QueueHandle();
    UART_QueueHandle();
    ...               /* 加一个驱动就要改 main */
}

/* ✅ 注册式 */
while (1) {
    LOOP_EVENT_Handle();    /* 驱动自己注册进来 */
}
```

**⇒ 加新驱动时 `main.c` 一行都不用改 ✓**

## 三、驱动层之一：UART —— **整个框架最值得学的设计**

**这是四个文件里设计得最漂亮的一个。**

### 3.1 核心：`HAL_UARTEx_ReceiveToIdle_DMA`

```c
HAL_UARTEx_ReceiveToIdle_DMA(huart, user_uart->rx_buffer_a, UART_BUFFER_SIZE);
```

**它同时用上了两个硬件特性：**

| 特性 | 作用 |
|---|---|
| **DMA** | 数据自动搬进内存，**CPU 零占用** |
| **空闲中断（IDLE）** | 总线空闲一个字符时间就触发 → ⭐ **天然的分帧！** |

**⇒ 解决了一个经典难题：UART 不知道怎么"收不定长数据"。**

```
DBUS 固定 18 字节   ┐
调参指令变长        ├─ 长度不固定，怎么知道收完了？
裁判系统变长        ┘
        ↓
【空闲中断】帮你判断"这一包发完了" ✓
```

**⇒ 优雅、省 CPU、代码少。**

### 3.2 ⭐⭐ 双缓冲（ping-pong）

```c
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size) {
    if (uart->is_buffer_a) {
        HAL_UARTEx_ReceiveToIdle_DMA(huart, uart->rx_buffer_b, ...);   /* ① 先重启 DMA 到 B */
        __HAL_DMA_DISABLE_IT(huart->hdmarx, DMA_IT_HT);
        RingBuffer_Put(&uart->rx_ringBuffer, uart->rx_buffer_a, Size); /* ② 再处理 A */
        uart->is_buffer_a = 0;
    } else { /* 反过来 */ }
}
```

**⭐ 注意顺序：先重启 DMA 到另一个 buffer，再处理当前 buffer。**

```
DMA 正在写 buffer_b  ─┬─ 同时 CPU 处理 buffer_a  ✓ 无竞争
                      │
DMA 写完了 b，触发中断 → 重启到 a → 处理 b
```

**⇒ 避免了"边收边处理"的竞态。**

### 3.3 ⭐⭐⭐ 两级缓冲：**解耦"接收时序"和"处理时序"**

```
硬件 FIFO
   ↓ DMA（硬件自治）
DMA 缓冲（a/b）          ← 一级：接收时序，一个字符时间就写
   ↓ 中断里搬运
环形缓冲 ringBuffer      ← 二级：处理时序，上层按需取
   ↓ 主循环 callbacks[]
应用逻辑
```

**⇒ 为什么要两级？**

| 只有 DMA 缓冲 | 加 ring buffer |
|---|---|
| 上层必须**立刻**处理，否则下一包覆盖 ⚠️ | ✅ **可以慢慢处理**，数据不丢 |
| 处理逻辑必须写在中断里 ⚠️ | ✅ 可以放到主循环/任务里 |

**⭐⭐ CSC 里的经典思想：用缓冲解耦生产者和消费者的**时间约束**。**

### 3.4 发送：队列 + 中断驱动（非阻塞）

```c
void UART_Send_Data(UART_DRIVES* u, const char* data, uint16_t len) {
    Queue_Push(&u->tx_queue, (char*)data, len);      /* 只入队，立刻返回 ✓ */
}

static void UART_QueueHandle(void) {                  /* 主循环里 */
    if (!Queue_IsEmpty(&u->tx_queue)) {
        if (u->status == UART_IDLE) {
            const Node* temp = Queue_Pop(&u->tx_queue);
            HAL_UART_Transmit_DMA(u->huart, temp->data, temp->len);
            u->status = UART_SENDING;
        }
    }
}

void HAL_UART_TxCpltCallback(UART_HandleTypeDef *huart) {
    if (u->tx_queue.popped) {
        Queue_FreeNode(u->tx_queue.popped);           /* ★ 发送完才释放内存 */
        u->tx_queue.popped = NULL;
        u->status = UART_IDLE;
    }
}
```

**⭐⭐ 三个学习点：**

| # | 设计 | 好处 |
|---|---|---|
| **1** | **`UART_Send_Data` 只入队** | **非阻塞** —— 调用方不管 UART 忙不忙 ✓ |
| **2** | **`status` 状态机** | `IDLE` / `SENDING`，防止重入 ✓ |
| **3** | ⭐ **`popped` 指针 + `TxCplt` 里释放** | **内存池化** —— 只有发送完成才归还节点 ✓ |

**⇒ 这套"队列 + 状态机 + 完成回调"是**所有异步发送**的标准模式**（CAN、SPI、网络都适用）。

### 3.5 错误恢复（很少人写，但很重要）

```c
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart) {
    HAL_UART_DMAStop(huart);
    __HAL_DMA_DISABLE(hdma);
    __HAL_UART_CLEAR_OREFLAG(huart);    /* 溢出 */
    __HAL_UART_CLEAR_NEFLAG(huart);     /* 噪声 */
    __HAL_UART_CLEAR_FEFLAG(huart);     /* 帧错误 */
    __HAL_UART_CLEAR_IDLEFLAG(huart);
    /* 重启 DMA */
}
```

**⭐⭐ 为什么必须写：**

```
UART 出错（比如线被拔了、干扰）→ HAL 会停止 DMA
        ↓
如果不重启 → 【这个串口就永久死了】直到复位 ✗
        ↓
⇒ 错误回调里必须 "清标志 + 重启" ✓
```

**⇒ 教训：异步外设一定要有"错误恢复路径"，否则一个瞬时故障会变成永久故障。**

### 3.6 封装成 `printf` / `scanf`

```c
void UART_Printf(UART_DRIVES* u, const char* format, ...);   /* vsnprintf → 入队 */
int32_t UART_Scanf(UART_DRIVES* u, const char* format, ...); /* 取全部 → vsscanf */
```

**⇒ 把串口做得"像标准库"，调试代码写起来极快 ✓**

**⚠️ 注意 `Printf` 里的 `buffer` 是 `static`** —— 非线程安全，但在单任务环境里没问题 ✓

## 四、驱动层之二：CAN

### 4.1 过滤器：全通 + 软件过滤

```c
can_filter.FilterIdHigh = 0x0000;
can_filter.FilterMaskIdHigh = 0x0000;    /* Mask = 0 → 全部通过 */
can_filter.FilterFIFOAssignment = CAN_RX_FIFO0;
```

**⇒ 硬件不过滤，全部收上来，由软件按 `fdb_id` 匹配。**

| 优点 | 缺点 |
|---|---|
| 简单、灵活（换电机不用改过滤器）| ⚠️ **CPU 要处理总线上的所有帧** |

**⇒ 电机少的时候没问题；如果总线负载高，应该改成"按 ID 硬件过滤"来降 CPU。**

### 4.2 ⭐⭐ 发送：`Peek` → 发送 → **成功才 Discard**

```c
if (Circular_Queue_Peek(&can->tx_queue, (uint8_t*)&tx_msg)) {   /* 只偷看，不出队 */
    ...
    if (HAL_CAN_AddTxMessage(...) == HAL_OK) {
        Circular_Queue_Discard(&can->tx_queue);                 /* ★ 成功了才丢 */
    }
}
```

**⭐⭐ 这是"可靠队列"的经典写法：**

```
Peek（偷看）→ 尝试操作 → 成功才 Discard
        ↓
如果失败了 → 节点还在队列里 → 下一轮自动重试 ✓
```

**对比"Pop 了再发"：**

```c
/* ❌ 崩了/失败了，数据就丢了 */
const Node* n = Queue_Pop(&q);
if (HAL_CAN_AddTxMessage(...) != HAL_OK) { /* 数据没了 */ }
```

**⇒ 教训：涉及"有失败可能"的操作，用 `Peek + Discard` 而不是 `Pop`。**

### 4.3 回调分发：数组 + 遍历

```c
for (uint8_t i = 0; i < can_drive->callback_num; i++) {
    can_drive->callbacks[i](can_drive);
}
```

**你工程里只注册了一个回调 `DJI_Motor_Handle`，它在里面遍历所有电机：**

```c
static void DJI_Motor_Handle(void* user_can) {
    for (motor_index = 0; motor_index < motor_num; motor_index++) {
        motor = motor_drives[motor_index];
        if (motor->can->hcan != can->hcan || motor->fdb_id != can->rx_msg.StdId)
            continue;
        motor->rx_count++;                      /* ← 我们加的掉线检测 */
        /* 解析 + 跑 PID */
    }
}
```

**⚠️ 这是 O(n) 遍历：5 个电机时，每收到一帧要比较 5 次。**

**⇒ 优化空间：用 `switch (StdId)` 直接分派，或者建 ID→电机 的查找表。**

**⚠️ 另一个隐患：`CAN_QueueHandle` 每轮主循环只发**一帧**（只 `Peek` 一次）。**

```
如果队列积压了 6 帧
        ↓
主循环要转 6 圈才能排空
        ↓
高负载时可能积压 ⚠️
```

**⇒ 改进：一轮里用 `while` 把所有能发的都发掉。**

## 五、驱动层之三：DJI 电机（`user_dji_motor.c`）

### 5.1 ⭐⭐ ID 规则集中在一处

```c
switch (user_motor->controller_type) {
    case GM6020_Controller:
        user_motor->fdb_id = GM6020_FEEDBACK_BASE_ID + id;      /* 0x204 + id */
        if (1 <= id && id <= 4) user_motor->ctrl_id = GM6020_CURRENT_CONTROL_ID_1;
        if (5 <= id && id <= 7) user_motor->ctrl_id = GM6020_CURRENT_CONTROL_ID_2;
        break;
    case C620_Controller:
    case C610_Controller:
        user_motor->fdb_id = C6x0_FEEDBACK_BASE_ID + id;        /* 0x200 + id */
        if (1 <= id && id <= 4) user_motor->ctrl_id = C6x0_CURRENT_CONTROL_ID_1;
        if (5 <= id && id <= 8) user_motor->ctrl_id = C6x0_CURRENT_CONTROL_ID_2;
        break;
}
```

**⭐ 学习点：把"协议规则"封装在 `Init` 里，上层只需要传 `型号 + ID`。**

**对比：**

```c
/* ❌ 让使用者自己写 0x205 / 0x1FE */
motor.fdb_id = 0x205;
motor.ctrl_id = 0x1FE;

/* ✅ 传语义 */
DJI_Motor_Init(&motor, &can, 1, 0, GM6020, Rotor_angle, &pid);
```

**⇒ 教训：让 API 接受"领域概念"（型号、ID），而不是"寄存器值"。**

### 5.2 ⭐⭐ 统一限幅：功率预算 → 电流上限

```c
const int16_t current_limit =
    (int16_t)(motor->power_limit / BUS_VOLTAGE / C620_MAX_CURRENT * 16384.0f);

if (current_target >  current_limit) current_target =  current_limit;
if (current_target < -current_limit) current_target = -current_limit;
```

**⇒ 把"功率(W)"折算成"电流刻度"，然后夹住 PID 输出。**

**⚠️ 注意：这个公式**对 GM6020 也用了**，但 GM6020 的电流帧量程是 ±3000 而不是 ±16384。**

**⇒ 所以云台功率设成 90W，正好折算成 3072 ≈ 满量程（这是"凑"出来的）。**

**⇒ 教训：**统一处理能减少代码，但要注意量纲/量程的差异。** 更严谨的做法是让 `motor_type` 参与换算。**

### 5.3 编码器回绕的正确处理

```c
/* 编码器 0~8191，周期是 8192 不是 8191，否则每次回绕丢 1 个脉冲 */
if (delta_angle >=  4096) delta_angle -= 8192;
else if (delta_angle <= -4096) delta_angle += 8192;

motor->total_angle += delta_angle;
```

**⭐⭐ 两个学习点：**

| # | 点 |
|---|---|
| **1** | **周期是 8192 不是 8191** —— 13 位编码器有 8192 个状态。用 8191 会**每圈丢 1 个脉冲**（累计误差）|
| **2** | **用"绝对值差分"累积多圈角** —— 丢帧也不会累积错误（因为 `rotor_angle` 是绝对的）✓ |

**⇒ 这是"绝对式编码器读多圈角度"的标准做法。**

### 5.4 组帧：一带四

```c
switch (motor->ctrl_id) {
    case C6x0_CURRENT_CONTROL_ID_1:      /* 0x200 */
        C6x0_control_id_1_frame[2 * motor->id - 2] = (uint8_t)(current_target >> 8);
        C6x0_control_id_1_frame[2 * motor->id - 1] = (uint8_t)(current_target >> 0);
        C6x0_control_id_1_sign = 1;
        break;
    ...
}
...
if (C6x0_control_id_1_sign) CAN_Send(can, C6x0_CURRENT_CONTROL_ID_1, ...);
```

**⭐⭐ 两个学习点：**

| # | 设计 |
|---|---|
| **1** | **`2 * id - 2` 算出字节偏移** —— 每个电机占固定 2 字节槽位 ✓ |
| **2** | ⭐ **`_sign` 标志位：只有真的有电机用了这一帧才发** ✓ |

**⇒ "按需发帧"能省总线带宽。如果某条总线上没有 GM6020，就永远不发 `0x1FE`。**

## 六、算法层：PID（`user_pid.c`）

### 6.1 ⭐⭐ 接口结构体 —— C 里的"面向对象"

```c
typedef struct {
    CONTROLLER_INTERFACE_FUNC       /* ← 展开是一堆函数指针 */
    float kp, ki, kd;
    float max_out, max_iout;
    float set, fdb, out;
    float Pout, Iout, Dout;
    float err[2];
} PID_Controller;
```

**`CONTROLLER_INTERFACE_FUNC` 展开后大致是：**

```c
void  (*Set_Target)(void*, float);
float (*Calculate)(void*, float, float);
float (*Get_Output)(void*);
void  (*Set_MaxOut)(void*, float);
float (*Get_MaxOut)(void*);
```

**⭐⭐ 为什么这么设计：**

```c
/* 电机驱动拿到的是 CONTROLLER_INTERFACE*，不知道具体是 PID */
DJI_Motor_Init(..., (CONTROLLER_INTERFACE*)&user_wheel_pid_fl);

/* 内部只调接口 */
motor->controller->Calculate(motor->controller, speed, current);
```

**⇒ 想换成 ADRC / 模糊 / 前馈控制器？只要实现同一套接口，**电机驱动一行都不用改** ✓**

**⇒ 教训：面向对象不是只有 C++ 能做 —— 「结构体装函数指针 + `void*` 上下文」就是 C 的虚函数表。**

### 6.2 `Calculate` 的两个反馈参数

```c
float PID_Calculate(void* controller, const float main_feedback, const float sub_feedback);
```

**你工程里的用法：**

```c
case Rotor_speed:
    controller->Calculate(controller, Get_Speed(motor), Get_Current(motor));
    /*                              ↑ 主反馈（算误差）  ↑ 副反馈（备用） */
    break;
case Rotor_angle:
    controller->Calculate(controller, Get_Angle(motor), Get_Speed(motor));
    break;
```

**⇒ "副反馈"是给**串级控制**预留的接口**（比如角度环里，副反馈是速度，用于前馈/阻尼）。

**⚠️ 当前实现里 `sub_feedback` 没被使用（参数名都没接）。这是"预留接口"。**

### 6.3 实现：标准位置式 PID + 双重限幅

```c
pid->err[0] = pid->set - pid->fdb;
pid->Pout = kp * err[0];
pid->Iout += ki * err[0];
pid->Dout = kd * (err[0] - err[1]);

/* 积分限幅（抗饱和） */
if (Iout > max_iout) Iout = max_iout; ...

float out = Pout + Iout + Dout;

/* 输出限幅 */
if (out > max_out) out = max_out; ...

pid->err[1] = err[0];
```

**✅ 做得对的：**
- **积分限幅**（`max_iout`）→ 抗积分饱和 ✓
- **输出限幅** ✓
- **保存 `Pout/Iout/Dout`** → 便于调参时观察是哪一项在起作用 ✓

**⚠️ 相比工业级 PID 缺的（这正是"可以学"的地方）：**

| 缺失 | 后果 | 工业做法 |
|---|---|---|
| **积分分离** | 大误差时积分狂涨 → 超调 | 误差大时不积分（或减小 Ki）|
| **微分先行** | 目标突变时 D 项尖峰 | 对**反馈**微分，不对误差微分 |
| **D 项除以 dt** | ⭐ **D 项和采样率耦合** —— 改周期就要重调 Kd | `Dout = kd * (err[0]-err[1]) / dt` |
| **不完全微分** | D 对噪声敏感 | 加低通滤波 |
| **抗饱和反馈补偿** | 输出饱和时积分仍在涨 | back-calculation |

**⭐⭐ 最值得注意的一条：`Dout` 没有除以 `dt`。**

```
如果采样周期从 1ms 改成 2ms：
    err[0] - err[1] 会变成约 2 倍
        ↓
    同样的 Kd 会产生 2 倍的 D 输出
        ↓
    ⇒ 必须重新调 Kd ⚠️
```

**⇒ 教训：写 PID 时，D 项一定要归一化到"每秒"，否则参数不可移植。**

## 七、应用层：三个文件的分工

### 7.1 `chassis.c` —— 纯"对象"

```c
void Chassis_Update(Chassis* c) {
    Chassis_InverseKinematics(c->vx, c->vy, c->omega, c->speed);   /* 算法 */

    for (int i = 0; i < 4; i++) {
        c->rpm[i] = RAD_TO_RPM(c->speed[i] / c->wheel_r) * c->ratio * c->reverse[i];
        c->rpm_fdb[i] = c->wheel[i]->Get_Motor_Speed(c->wheel[i]);

        c->wheel[i]->Set_Power_Limit(c->wheel[i], c->power_limit);
        c->wheel[i]->Set_Motor_State(c->wheel[i], c->rpm[i]);
    }
}
```

**✅ 设计得很好：**
- **只做"运动学 → 电机指令"的转换**，不管遥控、不管模式 ✓
- **通过 `MOTOR_INTERFACE` 调用**，不认识具体电机型号 ✓
- **`reverse[]` 只在最后乘一次** —— 补偿点单一、清晰 ✓

**⭐⭐ 学习点：职责单一。** `chassis.c` 就干一件事，所以它**极难出错**，也**极好测试**。

### 7.2 `chassis_control.c` —— 策略层

**职责：遥控 → 速度 → 模式 → 航向补偿 → 交给 chassis**

```c
const uint8_t src_ok = s_source_valid();

const float vx =  Stick(RC_Channel(CHASSIS_RC_VX_CH)) * CHASSIS_MAX_VX;
const float vy = -Stick(RC_Channel(CHASSIS_RC_VY_CH)) * CHASSIS_MAX_VY;

#if CHASSIS_HEADING_COMP
    const float theta_rad = (src_ok ? Heading() : 0.0f) * DEG2RAD;
    const float cos_t = cosf(theta_rad), sin_t = sinf(theta_rad);
    vx_body = vx * cos_t - vy * sin_t;
    vy_body = vx * sin_t + vy * cos_t;
#endif

float omega = (s_mode == CHASSIS_MODE_FOLLOW) ? /* PID */ : Chassis_Spin_Omega();
if (!src_ok) omega = 0.0f;
omega *= s_omega_dir;
```

**⭐⭐ 学习点 1：可插拔的钩子**

```c
typedef float   (*Chassis_HeadingSource)(void);    /* 角度从哪来 */
typedef uint8_t (*Chassis_SourceValid)(void);      /* 这个角度可信吗 */

void ChassisControl_Set_HeadingSource(Chassis_HeadingSource source);
void ChassisControl_Set_SourceValid(Chassis_SourceValid valid);
```

**⇒ 默认是 `NoHeading()`（返回 0，退化为车体系直控），`main.c` 里再"插上"真正的源。**

**⇒ 好处：**
- **`chassis_control.c` 不知道有云台** ✓ 解耦
- **换角度源（编码器/IMU/双 yaw）只改一行注册** ✓
- **单元测试时可以插假数据** ✓

**⭐⭐ 学习点 2：在线调参表**

```c
static const SERIALPLOT_VAR chassis_tunable[] = {
    {"test_wheel", &s_test_wheel, -4.0f, 4.0f,   NULL},
    {"spin_w",     &s_spin_w,      0.0f, 20.0f,  NULL},
    {"wheel_kp",   &s_wheel_kp,    0.0f, 100.0f, Chassis_Apply_Wheel_Gain},
    ...
};

const SERIALPLOT_VAR* ChassisControl_Get_Tunable(uint8_t* count) {
    *count = sizeof(chassis_tunable) / sizeof(chassis_tunable[0]);
    return chassis_tunable;
}
```

**⭐⭐⭐ 这是整个应用层最聪明的设计：**

| 特点 | 价值 |
|---|---|
| **把"参数"当成"数据"** | 一张表驱动，加参数只加一行 ✓ |
| **带 min/max** | 自动限幅，避免误输入搞坏系统 ✓ |
| **带 `on_change` 回调** | 改完能触发副作用（比如重新写入 PID）✓ |
| **返回指针 + 数量** | 串口模块不用知道有哪些参数 ✓ |

**⇒ 结果：调参不需要重新编译烧录，**在线改、立刻生效**。**

**⇒ 教训：把"可调的东西"集中成数据表，是嵌入式调试效率的关键。**

### 7.3 `gimbal.c` —— 状态机 + 安全逻辑

```c
static void Gimbal_Update(void* arg) {
    /* ① 掉线检测：反馈计数不涨就累计超时 */
    if (gimbal->yaw_motor->rx_count != gimbal->last_rx_count) {
        gimbal->last_rx_count = gimbal->yaw_motor->rx_count;
        gimbal->offline_ms = 0;
        gimbal->is_online = 1;
        gimbal->has_ever_online = 1;
    } else if (...) { /* 超时 → is_online = 0; is_aligned = 0; */ }

    /* ② 观察字段 + 遥控目标（放在对齐判断【之前】，便于诊断）*/
    gimbal->angle_raw = DJI_Motor_Get_Angle(gimbal->yaw_motor);
    gimbal->speed = DJI_Motor_Get_Speed(gimbal->yaw_motor);
    if (user_dbus.is_update) gimbal->target_yaw = ...;

    /* ③ 首次对齐：还没对齐就不下发任何指令 */
    if (!gimbal->is_aligned) {
        if (!gimbal->is_online) return;
        Gimbal_Set_Zero(gimbal);
        gimbal->is_aligned = 1;
    }

    /* ④ 正常控制 */
    gimbal->yaw = Gimbal_Get_Yaw(gimbal);
    const float error = Gimbal_Wrap180(gimbal->target_yaw - gimbal->yaw);
    gimbal->yaw_motor->Set_Motor_State(gimbal->yaw_motor,
                                       gimbal->angle_raw + error * GIMBAL_YAW_DIR);
}
```

**⭐⭐ 学习点：**

| # | 设计 | 意图 |
|---|---|---|
| **1** | **用"计数值是否变化"判断在线** | ⚠️ **不能看角度变没变**（静止时角度本来就不变）→ 计数器是唯一可靠手段 ✓ |
| **2** | **`has_ever_online` 区分"从没连过"和"真掉线"** | 裸车调试不受保护干扰 ✓ **细腻** |
| **3** | **诊断字段放在提前 `return` 之前** | 即使没对齐也能从串口看到 `graw`/`gtgt` ✓ **可调试性** |
| **4** | **对齐完成前不发任何指令** | 绝对编码器上电会猛冲 → 用"等第一帧 + 以当前位置为零点"解决 ✓ |

**⭐⭐⭐ 第 3 条特别值得学：**
> **把"诊断用的状态"和"控制用的状态"分开维护，并保证诊断字段在**所有路径**下都更新。**
> **否则一旦某条路径提前返回，你就失去了观测能力 —— 变成"盲调"。**

## 八、⭐⭐ 可以学到的 9 个设计模式（提炼）

| # | 模式 | 在哪 | 价值 |
|---|---|---|---|
| **1** | **接口结构体**（结构体装函数指针 + `void*`）| `CONTROLLER_INTERFACE_FUNC`、`MOTOR_INTERFACE` | C 里的虚函数，可替换实现 |
| **2** | **注册式挂载** | `SysTick_InitTask`、`loop_event[]`、`CAN_RegisterCallback` | 驱动不认识使用者，解耦 |
| **3** | ⭐ **两级缓冲解耦时序** | UART：DMA 缓冲 + ring buffer | 生产者/消费者时间约束解耦 |
| **4** | ⭐ **`Peek` → 操作 → 成功才 `Discard`** | CAN 发送 | 可靠队列，失败自动重试 |
| **5** | **实例集中管理** | `bsp.c` + `bsp.h` | 一处定义一处导出，避免 extern 满天飞 |
| **6** | ⭐ **把参数变成数据表** | `chassis_tunable[]` | 加参数一行，在线调参 |
| **7** | **可插拔钩子** | `Chassis_HeadingSource` / `SourceValid` | 不改框架就能扩展 |
| **8** | **单变量双语义** | `delay` 复用为 `period` | 省内存、代码短 |
| **9** | ⭐ **诊断与控制分离** | gimbal 的 `angle_raw`/`speed` | 保证任何路径下都可观测 |

**还有两个"工程实践"级别的：**

| # | 实践 |
|---|---|
| **10** | **CubeMX 共存**：`USER CODE BEGIN/END` 钩子 + `tools/cubemx_postgen.ps1` 后处理 |
| **11** | **协议成帧交给硬件**：UART 空闲中断天然分帧，不用写状态机 |

## 九、⚠️ 框架的短板与改进空间

| # | 问题 | 影响 | 改进方向 |
|---|---|---|---|
| **1** | **SysTick 回调串行累加** | 任务总时间 > 1ms 就崩 | 加执行时间统计；把慢任务挪到别的时基 |
| **2** | **`task_count` 无越界检查** | 注册超限静默越界写 ⚠️ | 加 `if (task_count >= MAX) return;` |
| **3** | **CAN 回调 O(n) 遍历** | 电机多了效率低 | 用 `switch(StdId)` 或 ID→电机查找表 |
| **4** | **CAN 队列每轮只发一帧** | 高负载积压 ⚠️ | 改成 `while` 一次排空 |
| **5** | **CAN 过滤器全通** | CPU 处理所有帧 | 改成硬件按 ID 过滤 |
| **6** | ⭐ **PID 的 D 项未除以 dt** | 改采样率要重调 Kd | `Dout = kd * (err0-err1) / dt` |
| **7** | **PID 无积分分离 / 微分先行** | 大误差时超调 | 加工业级改进 |
| **8** | **`power_limit` 换算不区分电机型号** | GM6020 靠"凑 90W" | 按 `motor_type` 分别换算 |
| **9** | **软浮点（无 FPU）** | 三角函数/除法慢 | 开 FPU（要慎：中断里用 FPU 需压栈）|
| **10** | **没有故障日志/黑匣子** | 出问题难复现 | 加环形日志缓冲 |

## 十、总结：这套框架的"性格"

**✅ 它的优点：**

```
· 分层清楚，每层只干一件事
· 驱动层完全"不认识"具体实例（全靠指针 + 注册）
· 大量使用"表驱动"和"钩子"→ 扩展不用改框架
· 有完整的错误恢复路径（UART 错误回调）
· 把参数集中成数据表 → 在线调参
· 与 CubeMX 共存的工程实践很成熟
```

**⚠️ 它的短板：**

```
· 任务调度是"串行阻塞"的，没有时间保护
· PID 是教学级实现，缺工业级改进（D 未归一化最值得修）
· 一些地方 O(n) 遍历，规模上去会吃力
· 软浮点，数学运算偏慢
```

**⭐⭐ 最能学的一句话：**

> **这套框架的核心思想是「**驱动层只提供机制，应用层决定策略**」——**
> **驱动不知道谁用它（注册式）、不知道参数是什么（接口结构体）、不知道要跑多快（任务表）。**
> **结果就是：加功能不用改框架，改参数不用重编译。**
